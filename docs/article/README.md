## メイン記事の狙い

「エージェント的RAGは効果があるのか」という問いに対して、**「なかった」で終わらせない**のが軸。
これは記事の構成が2幕になったあとも変わっていない。

- **第1幕**: 初回は multihop 10/26 の完敗だったが、原因を追うと5つが実装バグと計測の交絡で、
  潰したら 17/26（単発ハイブリッドと同点）まで上がった
- **第2幕**: 引き分けで終わらせず、クエリ分解と記事多様化という工夫を2つ足したところ、
  統合方法の設計ミス（異なるクエリのスコアをそのまま比較）で一度regressionし、
  直したら 19/26 まで上がってハイブリッドを上回った。ただしこの最終的な2問差は
  自分たちで定めた「誤差」の閾値ぎりぎりで、絶対的な勝敗としては言い切れない

つまり「完敗」も「勝利」も、そのまま鵜呑みにせず**何を確認すべきか**を実測で示す、
という軸は一貫している。読者にとって一番実用的なのは、そのチェックリストの部分のはず。

「効果がなかった/あった」系の記事は多いが、**その結論を出す前に何を確認すべきか**を
実測で示している記事は少ない、という差別化。

## 書くときの注意

- **分散を測っていないことを隠さない。** 各条件1回ずつの実行なので、
  個々の実行間の2〜4問差は誤差。(a)→(f) の7問差の方向性は信頼できるが、
  最終的な「17→19」の2問差は自分で決めた誤差閾値の内側にあるので、
  「勝った」と断定せず「方向性としては支持される」くらいの書き方に留める
- 自分の判断ミス（単発の結果を根拠に何度も設計変更を重ねた、
  「マージ順が原因」と断定したが支持されなかった回もあれば、
  「複数クエリのスコア比較が原因」という当たりが的中した回もある）も両方書く。
  そこが「実験の進め方」の教訓として一番価値がある
- regressionを踏んだこと自体を隠さない。**新しい工夫を足したら一度悪化し、
  原因を切り分けて直したら改善した**、という顛末そのものが記事の山場になっている
- コーパスは自分のQiita記事20本という小規模。**一般化できる範囲を明示する**

## 続編（`03`）の狙い

`01` のような「問いを立てて切り分けた」記事にはしない。**手元に4090があるので同じものを
ローカルで回してみた**、という温度感で書く。最低限おさえるのは下の2つだけ。

1. **ローカルLLMでツール呼び出しはできるのか** → できた（構造化出力の失敗0件・指示追従性はむしろ良い）。
   ただし使い方は変わる（fetch 1/4）のに**精度は同じ**、が山場
2. **768次元のローカル埋め込みで検索は落ちるのか** → ハイブリッドでは同値、純ベクトルのみ −8pt

レイテンシ・コスト・API課金ゼロはスパイスとして1章にまとめ、主題には据えない。
計測の仕込み（`ToolUseStats`）と指紋照合は「**静かに壊れるのが怖かった**」という
体験ベースの節に留め、方法論として大きく展開しない。

`01` と同じく、分散を測っていないこと・回答品質を測っていないことは隠さない。
特に「性能は同程度」ではなく「**検索が正解を引く能力は同程度**」と限定して書く。

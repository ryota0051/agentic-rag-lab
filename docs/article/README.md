# 記事案

このリポジトリの実験内容を Qiita 記事に落とすための下書き置き場。

## 方針

素材を1本に詰め込むと長くなりすぎ、かつ「比較実験の話」と「日本語RAGの実装Tips」という
性質の違う読者層が混ざる。2本に分ける。

| ファイル | 内容 | 状態 |
|---|---|---|
| `01-agentic-vs-normal-rag.md` | **メイン。** 3パターン比較の結果と、そこに至るまでに潰した5つの落とし穴 | 全文ドラフト |
| `02-japanese-rag-lancedb-pitfalls.md` | 日本語コーパスでLanceDBを使うときの実装Tips。単独で完結する | アウトライン |

## メイン記事の狙い

「エージェント的RAGは効果があるのか」という問いに対して、**「なかった」で終わらせない**のが軸。

初回の結果は multihop 10/26 の完敗だったが、原因を追うと5つが実装バグと計測の交絡で、
潰したら 17/25（単発ハイブリッドと同点）まで上がった。

つまり最初の「完敗」は**エージェント的RAGではなく実装の質を測っていた**。
ここが読者にとって一番実用的な情報のはず。

「効果がなかった」系の記事は多いが、**その結論を出す前に何を確認すべきか**を
実測で示している記事は少ない、という差別化。

## 書くときの注意

- **分散を測っていないことを隠さない。** 各条件1回ずつの実行なので、
  個々の実行間の2〜4問差は誤差。(a)→(f) の方向性は信頼できるが、
  「(b) から (e) で+2問改善」のような語り方はしない
- 自分の判断ミス（単発の結果を根拠に4回チューニングした、
  「マージ順が原因」と断定したが支持されなかった）も書く。
  そこが「実験の進め方」の教訓として一番価値がある
- コーパスは自分のQiita記事20本という小規模。**一般化できる範囲を明示する**

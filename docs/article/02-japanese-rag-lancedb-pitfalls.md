## 狙い

メイン記事は「エージェント的RAGの比較実験」が主題なので、
**日本語でRAGを組む人が実際に困る話**は埋もれてしまう。

「LanceDB 日本語」「Tantivy 日本語 トークナイザ」で検索して来る人に届く形で、

## 構成案

### 1. 結論から

`lancedb.Index.fts({ baseTokenizer: "icu" })` を明示しろ。デフォルトだと日本語は引けない。

### 2. デフォルトで何が起きるか（実測）

| baseTokenizer | 合成データ | 実コーパス（記事20本/455チャンク） |
|---|---|---|
| `simple`（デフォルト） | 0/10 (0%) | 4/25 (16%) |
| `icu` | 10/10 | 23/25 (92%) |
| `ngram` (2-3) | 10/10 | 25/25 (100%) |

- LanceDB の全文検索は Tantivy ベース、デフォルトは空白と句読点で分割
- 日本語は分かち書きしないので、記事本文が実質1トークンになる
- **エラーも警告も出ない。検索結果が空になるだけ**
- 実コーパスで0%でなく16%なのは、`vLLM` `LanceDB` のようなASCII語だけは
  空白区切りでもトークン化されるから

### 3. 選択肢の比較

- `simple` … 却下
- `icu` … **推奨。** ICUの辞書ベース単語分割。外部モデルのダウンロード不要
- `ngram` (2-3) … 100%だが索引が肥大し、部分文字列一致のノイズが増える
- `lindera/ipadic` … 形態素解析として筋は良いが、外部辞書の配置と
  `LANCE_LANGUAGE_MODEL_HOME` の設定が必要

**ngramの100%を額面通りに受け取らない話**（測定の限界）をここで書く。
「本文から抜いた語で検索して元チャンクが返るか」という測定は構造的にngramに有利。
部分文字列検索が部分文字列を見つけるのはほぼ同語反復であり、
ランキング品質の証拠にはならない。

### 4. 検証を自動化する

```bash
npm run verify-fts            # コーパスから語を自動抽出して合格率を出す
npm run verify-fts -- --compare  # トークナイザを張り替えて比較
```

- テスト語はコーパスから自動抽出する（記事内容へのハードコードを避ける）
- 「出現チャンク数が少ない＝識別力が高い語」を選ぶ
- 合格率80%未満で exit 1 にして、CIのゲートにできる
- 埋め込みを再計算しないのでAPIコストはかからない

### 5. TypeScript SDK の注意点

- Python にある `.vector()/.text()` パターンがない。埋め込みを自前で計算して
  `.nearestTo()` に渡す
- `RRFReranker` は**リランカーではなく順位融合**。名前に惑わされない
  （Cross-Encoderによる意味的な再スコアリングとは別物）

```ts
const reranker = await lancedb.rerankers.RRFReranker.create();
const results = await table.query()
  .fullTextSearch(query)
  .nearestTo(queryVector)
  .rerank(reranker)
  .limit(k)
  .toArray();
```

### 6. おまけ：チャンク分割で見出しパスを持たせる

- 見出し（`##` / `###`）でセクションに切る
- `記事タイトル > セットアップ > Docker` のような**見出しパス**をメタデータに持たせ、
  本文の先頭にも前置する
- 効能は3つ:
  - チャンク単体で読んだときに文脈が分かる
  - embedding と BM25 の両方が見出しの語を利用できる
  - fetch の範囲拡張（同一セクションの兄弟チャンク取得）の単位になる

### 7. まとめ

日本語RAGは「動いているように見えて片肺」になりやすい。
BM25側が死んでいてもハイブリッド検索は結果を返すので、気づけない。
**インデックス構築の直後に検証ステップを挟む**こと。

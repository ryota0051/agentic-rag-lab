## 温度感

`03` と同じく「流行っているらしいので、手元の実験装置に差し込んでみた」で書く。
問いは1つだけ: **「次に何をすべきか」を判定するモデルは、エージェントの「検索はもう十分か？」の判定に使えるのか。**

## 全体の結論（冒頭か最後に置く1段落）

> 判定を Jev に替えても精度は落ちず、コストは1割強下がった。判定そのものは18倍速いが、エージェント全体の応答時間はほぼ変わらない。
> いちばんの違いは、判定が「確率」で返ってくること。**Jev が間違えるのは確率が中間のときだけ**だったので、迷っているケースを閾値で扱えるようになった。

| 主張 | 数値 | 根拠 |
|---|---|---|
| 精度は落ちない | 完全ヒット 16 → 17／26、部分recall 73.1% → 80.8% | e2e「agentic の LLM 判定版と Jev 判定版」 |
| コストは下がる | 入力トークン 60,394 → 51,874（−14%）、LLM呼び出し 12.8 → 11.7 | 同上 |
| 判定単体は速い | 判定1回の中央値 LLM 3,212ms → Jev 180ms（約18倍） | gate「揺れ・速度・コスト」 |
| 全体は速くならない | 平均 36.9s → 34.9s（−5%）、中央値 23.3s → 31.8s（悪化） | e2e 同表 |
| 間違えるのは中間の確率のときだけ | LLM と判定が分かれた17件は、Jev の p がすべて 0.21〜0.54 | gate「LLM と Jev で判定が分かれたもの」 |

**「速くなった」とは書かないこと。** 速いのは判定ステップ単体の話で、1問を答え切る時間はほぼ同じ。
理由（1問あたり約12回の LLM 呼び出しのうち、判定は1〜2回しかない）も添える。

## ② エージェントライクな判断ができるか確認

パターン3には LLM に二値を言わせている判定ステップが4つある。そのうち2つを Jev に置き換えて、オフラインで比べた。

### 2-0. どこに差し込めるか（棚卸し）

| 判定ステップ | Jev に任せた部分 | 正解ラベル | 判断 | 根拠 |
|---|---|---|---|---|
| スキル分岐（検索するか／直接答えるか） | 全体 | boundary-cases 20件 | 試す | ADR「判定ステップの棚卸しと提案」 |
| 収集完了の判定（もう十分か） | 「十分か」だけ。不足時に何を探すかは LLM | 正解 chunk が揃っているか | 試す（本命） | 同上 |
| 質問分解の要否 | — | — | 見送り。分解すると判定されたら結局 LLM が要る | 同上 |
| 回答後の確信度チェック | — | — | 見送り。収集完了判定と役割が重なる | 同上 |

**書くポイント**: Jev は文章を出せない。「十分か」は Jev、「何が足りないか」は LLM、と**判定と生成を分業させる**のが設計の要。

### 2-1. スキル分岐（検索するか、直接答えるか）

### 2-2. 収集完了の判定（もう十分か）← 本命

**実験設計の説明（短く）**: エージェントは回さず、検索だけで「根拠のスナップショット」を184件作った。正解ラベルは「正解 chunk が揃っているか」。

| スナップショット | 作り方 | 件数（うち十分） |
|---|---|---|
| natural_k5 | 検索上位5件 | 46（34） |
| natural_k2 | 検索上位2件 | 46（23） |
| forced_full | 正解を必ず含めた5件 | 46（46） |
| drop_one | 正解を1件抜き、その記事ごと除外して検索し直した5件 | 46（0） |

| 書くこと | 数値 | 根拠 |
|---|---|---|
| 分離性能は高い | ROC AUC: noul 0.962 ／ score 0.951 | gate「結果」 |
| 閾値は既定の 0.5 のまま、正解率は同等で見逃しが約半分 | 正解率 LLM 86% / 88%、Jev 87%。見逃し LLM 12 / 10、Jev 5。空振り LLM 13、Jev 19 | gate「結果」 |
| 閾値で運用点を選べる（LLM は1点だけ） | τ=0.4: 見逃し 10 ／ 空振り 10（LLM を両軸で下回る）。τ=0.7: 見逃し 2 ／ 空振り 29 | 同上 |
| 確率がそのまま信頼度として読める | p の区間ごとの実際の十分率: 4% → 28% → 73% → 88% → 97% | gate「キャリブレーション」 |
| 揺れは LLM の1/3 | 2回で判定が割れた件数: LLM 6、Jev 2 | gate「揺れ・速度・コスト」 |
| **得意**: 話題は合っているのに肝心の記述が無い | drop_one: Jev 96%、LLM 87% / 89% | gate「種類ごとの内訳」 |
| **苦手**: 全部揃っているのに自信が持てない | forced_full: Jev 74%、LLM 83% / 80% | 同上 |
| 苦手の具体例 | 「Amazon Bedrock の Converse API … モデルIDとシステムプロンプトは何ですか？」が3つのスナップショットすべてで 0.29〜0.44。切り詰めは原因ではない（正解 chunk は 539〜679 字で全文入り） | gate「種類別に見ると」 |
| 間違えるのは中間の確率のときだけ | 判定が分かれた17件は、すべて p=0.21〜0.54 | gate「LLM と Jev で判定が分かれたもの」 |

**書くポイント**: 「得意／苦手」は ADR 0008 の話（LLM は「だいたい関連しているから十分」と言いがち）とつながる。Jev はその逆の癖（揃っていても慎重）を持つ。
**書き方の注意**: ラベルは「正解 chunk が揃っているか」で、真の充足度ではない。「空振り」にはラベル側の誤りが混ざりうる。

### この章の着地

「確率で返るので、エージェントの『もう十分？』を**閾値という数値で**調整できる。
間違えるのは迷っているときだけ」。これが③で実際に組み込む動機になる。

## ③ どのように変わったか（パターン3に組み込んだ結果）

### 変えたもの

収集完了の判定だけを Jev に差し替えた（`DECISION_BACKEND=jev`、τ=0.5）。p(十分) ≥ 0.5 なら収集を終える。不足のときだけ LLM が「何が足りないか」を書く。
生成モデル・プロンプト・検索・インデックスは同一。対照群は同日・同条件の LLM 判定版。

### 書く内容

| 書くこと | LLM 判定 | Jev 判定 | 根拠 |
|---|---|---|---|
| 完全ヒット | 16/26（62%） | 17/26（65%） | e2e 比較表 |
| 部分recall | 73.1% | 80.8% | 同上 |
| 入力トークン（1問平均） | 60,394 | 51,874（−14%） | 同上 |
| LLM 呼び出し（1問平均） | 12.8 | 11.7 | 同上 |
| レイテンシ 平均 / 中央値 | 36.9s / 23.3s | 34.9s / 31.8s | 同上 |
| 10ターン以上回った問題 | 6問 | 4問 | e2e「agentic の LLM 判定版と Jev 判定版」の箇条書き |
| 3ターン以下で止まった問題 | 12問 | 10問 | 同上 |

### 定性観察（問題ごと）

| 種類 | 質問（略） | 何が起きたか | 根拠 |
|---|---|---|---|
| Jev が勝ち | houtini/lm でドキュメント生成に向いている理由 | LLM 版は3ターンで「十分」と言って止まり、片方の記事しか取れていなかった。オフライン比較でも LLM の判定が割れていた問題 | e2e「問題ごとに見ると」 |
| Jev が勝ち | CIFAR-10 の Optimizer 実験と vLLM×Qwen3×cline | LLM 版は12ターン回しても片方が取れず、Jev 版は10ターンで両方を回収 | 同上 |
| Jev が負け | curl で Qwen3-8B-FP8 の `<think>` を除外 | Jev 版が2ターンで「十分」と判定して止まった。**Jev にも見逃しはある**（閾値付近で起きる） | 同上 |
| 空回りを早めに切った | Vite+React と vLLM+Jupyter の Docker 構成 | LLM 版は15ターン・27呼び出しで部分recall 0。Jev 版は5ターン・7呼び出しで 0.5 | 同上 |
| 空回りを早めに切った | 日本語ローカルRAGの発展 | LLM 10ターン → Jev 5ターン（どちらも recall 0） | 同上 |

### 書くポイント

1. **トークンが減ったのは予想外だった。** オフライン比較の段階では「空振りが増えるぶんトークンも増える」と予想していた。実際には、十分と判定された回で LLM の判定呼び出しが無くなる効果と、空回りを早めに切る効果が上回った
2. **空回りは判定器ではなく検索側の限界。** LLM 版が15ターン回って何も取れなかったのは、「足りない」と言えても検索がそこへ辿り着けないため。判定器を替えても解決しない（`01` の課題がまだ残っている）
3. **全体のレイテンシはほぼ同じ。** 中央値が伸びたのは、3ターン以下で打ち切る問題が減ったため（早めに諦める問題も減った）

### 書き方の注意（必ず入れる）

- **n=26 で各1回。** 1問差はノイズの範囲（LLM 版 agentic は 2026-08-16 に 63%、今回 62%）。「Jev の方が良い」と断定しない。言えるのは「**替えても精度は落ちず、トークンは減る**」まで
- 閾値は事前に決めた 0.5 から動かしていない。オフラインの表では 0.4 の方が見栄えがよいが、同じデータで選んだ値になるので使わなかった。これは**誠実さのアピールポイント**として書いてよい
- 既定は LLM のまま残した理由（過去の実験と比べられなくなる、Jev は API 専用でローカル完結が崩れる）。ADR「既定を llm のままにする理由」

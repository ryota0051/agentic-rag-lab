# 0006. grep は開発初期の補助ツールに限定し、本番の検索経路に入れない

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/search/hybrid-search.ts`

## 背景

エージェント的検索の文脈では、エージェントに grep 的なツールを与えて
反復検索させるアプローチがしばしば紹介される。本プロジェクトでも
検索スキルのツール候補として検討した。

## 決定

**grep を本番の検索パイプラインに組み込まない。**
インデックス構築前に `data/raw/` の Markdown を直接調べたい開発初期の段階でのみ、
シェルから手で使う補助ツールとして位置づける。

## 理由

### grep と BM25 は同系統だが本質的に異なる

どちらも「文字列としての一致」に基づく検索だが、

- **grep** … マッチ / 不一致の**二値**で完了する。順位付けの概念がない
- **BM25** … TF-IDF 的な関連度でスコアを与え、**ランキングできる**

RAG で必要なのは「上位k件を選ぶ」ことなので、ランキングできることが本質的に効く。

### LanceDB の全文検索がその役割をすでに担っている

LanceDB の FTS は Tantivy ベースで BM25 相当のランキングを提供する。
「専門用語・固有名詞の完全一致」という grep に期待していた役割は、
すでにハイブリッド検索の BM25 側が担っている。
grep を足しても機能が重複するだけで、エージェントに与えるツールが増える分だけ
選択を誤る余地が広がる。

### 比較実験の変数が増える

パターン2とパターン3は同一の検索器を共有し、差分をループの有無だけに限定している
（`0005-no-cross-encoder-rerank.md` と同じ論法）。パターン3にだけ grep を与えると
差分が2変数になり、改善の原因を切り分けられなくなる。

## 補足: 日本語では grep の弱点がより際立つ

日本語は分かち書きしないため、grep による部分文字列一致は
語境界を無視したノイズを拾いやすい（「京都」で「東京都」にマッチする類）。
BM25 側は形態素/ICU 分割を通すことでこの問題を回避している
（`0007-japanese-fts-tokenizer.md`）。

## 帰結

- 検索スキルがエージェントに与えるツールは `search` と `fetch` の2つのみ
- 開発初期に `data/raw/` を調べる用途では、シェルの `rg` / `grep` を直接使えばよく、
  コードとして持つ必要はない

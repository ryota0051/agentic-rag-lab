# 0014. 埋め込みバックエンドをローカルに切り替えられるようにする

- 状態: 採用
- 日付: 2026-09-01
- 関連: [`0013`](0013-local-llm-backend.md)（生成バックエンド）、[`0007`](0007-japanese-fts-tokenizer.md)（日本語FTS）

## 背景

`0013` で生成・エージェントだけをローカル（Qwen3.8-27B / llama.cpp）に倒せるようにした。
残る OpenAI 依存は**埋め込み**と **LLM-as-judge** の2つ。

このうち埋め込みをローカル化できると、新しい実験軸が立つ。3パターン比較が
「検索戦略とループの有無」を、`0013` が「エージェントを駆動するLLM」を変数にするのに対し、
ここでは **retrieval そのものの質**を変数にできる。具体的には
「日本語特化の小型埋め込みは、3072次元のクラウドAPIに対してどこまで retrieval を保てるか」。

副次的に、judge を除けばローカル完結で実験を回せるようになる（API課金なしで反復できる）。

## 決定

`EMBEDDING_BACKEND` 環境変数（`openai` 既定 / `local`）で埋め込みを切り替える。
モデル・次元・prefix・pooling・バッチサイズは `src/shared/llm-client.ts` の
**埋め込みプロファイル表**（`EMBEDDING_PROFILES`）に集約し、そこが唯一の定義箇所になる。

`EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` はプロファイル由来の派生値として export 名を維持した。
既存の import はすべてそのまま動く。

### `LLM_BACKEND` と独立の軸にした理由

従属させると「生成はクラウドのまま・埋め込みだけローカル」という組み合わせが作れなくなる。
これは検索側だけを変数にした最も素直な比較であり、**実験軸は1本ずつ動かす**という
`0013` の原則からすると、むしろこの組み合わせこそが主役になる。

運用上は「両方同時に local にして1本だけ回す」ことを禁じる（どちらの寄与か分離できない）。

## モデル選定

`ruri-v3-310m`（cl-nagoya）を既定、`bge-m3` をフォールバックに置く。

| モデル | 次元 | 日本語 retrieval | pooling / prefix |
|---|---|---|---|
| `text-embedding-3-large`（既定・クラウド） | 3072 | P@1 0.554 | — |
| **`ruri-v3-310m`**（ローカル既定） | 768 | **JMTEB 77.2（日本語SOTA）/ P@1 0.555** | mean / `検索クエリ: ` `検索文書: ` |
| `bge-m3`（フォールバック） | 1024 | P@1 0.541 | cls / なし |

ruri-v3-310m を選んだのは、**日本語 retrieval で text-embedding-3-large と同等**でありながら
310M パラメータ・Q8_0 で 337MB と小さく、CPU 実行が現実的だから。8192トークンまで扱える点も
本コーパス（平均412文字のチャンク）には十分すぎる。

`bge-m3` を残しているのは、ruri の GGUF が「ModernBERT + SentencePiece 対応のパッチ版
llama.cpp で変換」と明記されており、ピン留めしたイメージでロードできるか事前に分からなかったため
（結果は「未検証事項の解消」を参照）。XLM-RoBERTa 系の bge-m3 なら本家 llama.cpp が確実に対応する。

### 却下したもの

| 候補 | 不採用の理由 |
|---|---|
| `Qwen3-Embedding-0.6B` | 多言語 MTEB では強いが、**日本語 Retrieval で ruri-v3-310m に約9pt 劣る**。生成モデルと同じ Qwen 系で揃う美点はあるが、この軸で見たいのは retrieval の質そのもの |
| `multilingual-e5-large` | 動くが `query: ` / `passage: ` という別の prefix 規約を持ち、ruri と混在させると付け間違いを誘発する。日本語性能も ruri・bge-m3 に劣る |
| 大型の ruri（`ruri-v3-1b` 等） | CPU 実行では遅すぎる。310m で既に text-embedding-3-large と同等なので、大型化する動機がない |
| GPU 常駐の埋め込みサーバ | 24GB に 18GB の生成モデルが載っている。数百MBでも VRAM 競合の可能性を作ると `0013` の前提（生成の再現条件を固定する）が崩れる |
| Ollama の embed API | `0013` と同じ理由。pooling を実験条件としてフラグで直接書けない |
| compose の `${VAR}` 展開で pooling を切り替える | このファイルが「そのとき何で回したか」の記録でなくなる。サービスを分けて全フラグを literal に書く |

## CPU 実行にした理由

`docker/compose.yaml` の `llama-embed-*` には **GPU 予約を書いていない**。
`-ngl 0` を指定するだけでなく、そもそもコンテナに GPU を見せないことで、
指定漏れがあっても VRAM に触れない構成にしてある。生成サーバと同時起動できることが要件。

イメージは生成側の `server-cuda-b10450` ではなく**同じビルド番号の CPU 版
`server-b10450`** を使う。GPU 予約を外すと nvidia ランタイムが `libcuda.so` を注入せず、
CUDA ビルドが起動時にバックエンドをロードできない可能性があるため。
同一ビルド番号なので「同一ソースリビジョン」という再現性は保たれる。

実測スループットは 5.1 件/s（16スレッド）。455チャンクの `build-index` が約1.5分、
クエリ1本は数十msなので、検索のレイテンシに実質影響しない。

## インデックスの分離と fingerprint 検証（このADRの本体）

**埋め込みを差し替えられるようにすると、CLAUDE.md 不変条件3 に静かな破滅ケースが生まれる。**

3072次元と768次元なら LanceDB が次元不一致で落としてくれる。しかし
**次元が同じで意味が違うベクトル空間**（bge-m3 の1024次元と、別の1024次元モデル）は
検索が成功し、5件返り、それらしい回答が生成される。recall だけが静かに落ち、
壊れていることに誰も気づけない。`0013` の `ToolUseStats` が潰した
「もっともらしい正常値」の埋め込み版である。

二重の対策を入れた。

**1. インデックスを物理的に分ける。**
`DB_DIR` を `data/index-<プロファイルslug>/` にした（`data/index-openai-3large/`、
`data/index-ruri-v3-310m/`）。異なる埋め込みのベクトルが同じテーブルに混ざることが原理的に起きない。

**2. 指紋を照合する。**
`build-index` が `index-meta.json`（モデル・次元・pooling・prefix・FTSトークナイザ・
チャンク数・構築日時）を書き、`openChunksTable()` が現在の設定と突き合わせて
不一致なら**日本語で throw** する。照合は1プロセス1回にメモ化している。

sidecar JSON を選んだのは、(a) LanceDB を開く前に読めるので接続前に日本語で throw できる
（Arrow の次元不一致エラーは原因が読み取れない）、(b) `db.tableNames()` を汚さない、
(c) build-index に Arrow の明示スキーマが一切ない（投入データから推論）という美点を崩さない、
(d) `cat` で人間が読め実験レポートに貼れる、の4点。

sidecar だけでは手で書き換えられるので、**次元だけは実テーブルの `vector` 列
（`FixedSizeList.listSize`）から実測**して二段構えにしている。

`ftsTokenizer` の不一致だけは警告に留める。ベクトル空間は壊れず BM25 の質が変わるだけだから。

検証ゲートを全経路に効かせるため、`verify-fts.ts` が直接 `lancedb.connect(DB_DIR)` していた
2箇所も `openChunksTable()` に統一した。

## L2正規化を自前で行う

`embed.ts` はバックエンドを問わず**無条件に** L2 正規化を通す。

LanceDB の `nearestTo()` の既定距離は L2。単位ベクトル同士なら
`‖a−b‖² = 2 − 2·cos(a,b)` なので L2 の順位は cos の順位と完全に一致し、
既存パイプラインはこの前提の上に立っている（OpenAI の埋め込みは正規化済み）。

llama-server は `--embd-normalize` を持たず、pooling によっては非正規化ベクトルを返す。
そのまま L2 で引くと**意味的な近さではなくベクトルの長さ（≒トークン数）が順位を支配する**。
検索は成功し5件返り回答も生成されるため、レポートには嘘の数値が並ぶ。

正規化は冪等なので、既に単位ベクトルなら値は変わらない。よってバックエンドで分岐する必要がなく、
分岐が無い方が事故が起きない。

`.distanceType("cosine")` を指定する案は採らなかった。順位は同じで検索コードに手が入り
不変条件1（検索戦略以外は同一）が濁るうえ、**正規化バグを隠してしまう**。
正規化はこちらで保証し、`verify-embedding` が生ノルムを実測して守る。

## prefix を呼び出し側に露出させない

ruri v3 のような非対称モデルは、クエリと文書で別の prefix を要求する。
**付け忘れてもエラーにならず精度だけが落ちる。**

そのため `embed(texts, role)` の `role` は `embedQuery` / `embedBatch` の内側に閉じ込め、
role を受け取る公開関数は作らなかった。呼び出し側3箇所（`build-index.ts` /
`vector-search.ts` / `hybrid-search.ts`）は**無変更**で済んでいる。

prefix は埋め込みに渡すテキストにだけ付ける。LanceDB の `text` 列（BM25 の対象であり
fetch が返す本文でもある）に混ぜてはいけない。

## judge は OpenAI 固定のまま

`0013` の結論をそのまま維持する。golden set はこのモデルで生成されており、
判定側を差し替えるとものさし自体が変わって過去の実験レポートと比較できなくなる。

**埋め込みを動かせるようにした以上、judge はなおさら動かせない。**
ものさしを2本同時に動かすと何も測れなくなる。
したがって `LLM_BACKEND=local` かつ `EMBEDDING_BACKEND=local` でも `OPENAI_API_KEY` は必要。

## 検証ゲート: `npm run verify-embedding`

`verify-local-llm` と同じ思想の事前チェックを新設した（`evals/verify-embedding.ts`）。
**`build-index` の前に、インデックス無しで通ること**を設計原則にしている
（インデックスに依存させると「壊れた埋め込みでインデックスを作ってから壊れていると分かる」
順序になり、ゲートとして機能しない）。検証材料は `data/raw` から `chunkArticle()` で作る。

必須項目は 接続と次元一致 / 正規化 / 決定性 / 等方性 / prefix適用 / embedBatch の順序保証 /
意味的サニティ / 実コーパス retrieval サニティ の8つ。

特に重要な2つ:

- **等方性（ベクトル崩壊）** — pooling が壊れたモデルは「全部ほぼ同じベクトル」を返す。
  この状態でも検索は5件返り、回答も生成され、recall だけが静かに落ちる。
  無関係20文の総当たり cos の平均が 0.95 を超えたら失敗にしている。
- **実コーパス retrieval サニティ** — 見出しパスをクエリに仕立てて top-3 命中率を測る。
  「この埋め込みが検索として使い物になるか」を直接測る唯一の項目。

正規化の検査は**`embed.ts` を経由せず生 fetch でサーバを叩く**。`embed.ts` の出力で
ノルムを測ると、自分がかけた正規化のせいで必ず 1 になり同義反復になってしまう。

順序保証の検査は `batchSize * 2 + 3` 本で行う。**必ずバッチ境界を跨ぐ本数**にしないと、
ループの push 順や `sort((a, b) => a.index - b.index)` の欠落が表に出ない。

## 未検証事項の解消

計画時点で最大のリスクは「ruri の GGUF はパッチ版 llama.cpp で変換されており、
ピン留めした `b10450` でロードできないかもしれない」だった。

**実測の結果、`ghcr.io/ggml-org/llama.cpp:server-b10450` でそのままロードできた。**
ModernBERT アーキテクチャのサポートが upstream（PR #15641 / 2025-12-22）に入っており、
SentencePiece トークナイザ経路も含めて本家で動く。パッチ版は変換時にだけ必要だったことになる。

したがって `bge-m3` は現時点で使っていないが、プロファイル表と compose サービスは残す。
埋め込みモデルを1つに固定すると、次に別のモデルを試すときに再びこの設計判断からやり直しになるため。

## 結果（実測）

`npm run probe:retrieval`（生成を挟まない retrieval 単体の計測）で比較した。
golden set・チャンク分割・FTSトークナイザはすべて同一。

| | text-embedding-3-large (3072d/API) | ruri-v3-310m (768d/CPU) |
|---|---|---|
| easy ベクトル検索 | 19/20 (95%) / 部分recall 95% | 18/20 (90%) / 90% |
| easy ハイブリッド | 20/20 (100%) / 100% | 20/20 (100%) / 100% |
| multihop ベクトル検索 | 13/26 (50%) / 73% | 11/26 (42%) / 71% |
| **multihop ハイブリッド** | 16/26 (62%) / 81% | **17/26 (65%) / 83%** |

純粋なベクトル検索（パターン1）では 3072次元のクラウドAPIがわずかに上回るが、
**パターン2・3が使うハイブリッド検索では ruri-v3-310m が上回った。**
337MB の日本語特化モデルを CPU で回して、3072次元のクラウドAPIと同等以上の
retrieval が得られている。

BM25 側は両インデックスで完全に同一の結果（合格 23/25、失敗した検索語も同一）で、
FTS が埋め込みに依存しないことが実証された。`chunk_id` も両インデックスで一致するため
（チャンク分割は `data/raw` からのみ決まる）、**golden set は埋め込みをまたいでそのまま有効**。

## 運用ルール

1. 埋め込みを変えたら必ず `npm run build-index` を実行する（別ディレクトリに作られる）。
2. `npm run verify-embedding` を `build-index` の**前**に通す。
3. 実験レポートは**同じ埋め込み slug 同士でのみ**比較する。1つのレポート内の3パターンは
   常に同一の埋め込みで、埋め込み比較はレポート間で行う（その際は生成バックエンドと
   golden set を固定する）。レポート名は既定埋め込みのとき従来と同一で、変えたときだけ
   `emb-<slug>` が入る。
4. `LLM_BACKEND` と `EMBEDDING_BACKEND` を同時に動かさない。
5. `data/index-*` は再生成可能な生成物。`.gitignore` 済み。
6. 埋め込み実験中に `npm run ingest` を実行しない（`chunk_id` が動き golden set が全滅する）。
7. サービスの起動・停止は npm scripts を使う。`docker compose --profile ruri up -d` だけだと
   プロファイルを持たない生成サーバ（18GB）まで起動し、プロファイル指定なしの
   `docker compose down` はプロジェクト全体を落とす。scripts はサービス名を明示している。

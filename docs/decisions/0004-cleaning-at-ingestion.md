# 0004. 整形・ノイズ除去を ingestion 時に一度だけ行う

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/index/clean.ts`, `src/index/ingest-qiita.ts`

## 背景

RAG パイプラインで文書の整形（ノイズ除去、記法の正規化）をどこで行うかには
2つの選択肢がある。

- **fetch 時**: 本文を読み込むタイミングで毎回クリーニングする
- **ingestion 時**: インデックス構築時に一度だけクリーニングし、以後は整形済みを保持する

## 決定

**ingestion 時に一度だけ行う。** fetch 側ではノイズ除去を一切行わない
（fetch がやるのは結合・重複除去・メタデータ付与・予算管理のみ）。

## 理由

### 1. 効率

同じ文書が複数のクエリから何度も fetch される。そのたびにクリーニングを走らせるのは無駄。
とくにエージェント的RAGはループの中で繰り返し fetch するため影響が大きい。

### 2. 検索精度（こちらが本質的）

embedding と BM25 のインデックスは `text` カラムに対して作られる。
クリーニングを fetch 時点まで遅らせると、**インデックスはノイズ入りの生テキストに対して
作られる**ことになり、search 自体の精度が落ちる。

「検索は汚いテキストに対して行い、読み込みの時だけきれいにする」という
一貫性のない状態になってしまう。

### 3. 改善のしやすさ

クリーニングロジックを改善する際、インデックス再構築だけで済み、
search / fetch 側のコードに手を入れずに済む。

## Qiita API を使う理由もここにある

HTML スクレイピングではなく Qiita API v2（`GET /api/v2/users/{username}/items`）を使い、
`body` フィールドから **Markdown 本文を直接取得**している。

HTML 経由だとナビゲーション・広告・タグ残骸といった構造的ノイズが必ず混入し、
その除去に労力を割くことになる。API を使えば**そもそもノイズが発生しない**。
これは「除去する」より一段良い解決である。

## 実装で行っている整形

- 改行コードを LF に統一（CRLF が混ざると見出し正規表現と文字数カウントがずれる）
- 長大なコードブロックの切り詰め（既定20行）。技術記事なのでコードは検索対象として
  価値があるが、200行の設定ファイル全文はチャンクを食い潰して周囲の説明文を押し出す
- 画像記法を alt テキストのみに縮約
- Qiita 独自の `:::note` 記法のマーカー除去
- リンクの URL を落としてテキストのみ残す（URL は文字数を食い BM25 のノイズになる）
- HTML タグ残骸、水平線、行末空白、連続空行の正規化

## 破ってはいけない制約

**見出し構造を壊さないこと。** 次段の `chunking.ts` が `#` 見出しに依存して
意味的境界でチャンクを切っている。見出しを削ったり階層を変えたりすると
チャンク分割が崩れ、インデックス全体が作り直しになる。

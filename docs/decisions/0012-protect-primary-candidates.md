# 0012. 種検索の統合で主クエリの候補を保護する

- ステータス: 採択
- 日付: 2026-08-09
- 関連: `src/workflows/agentic-rag/search-fetch-loop.ts`
- 実測: regression 発生時 → `experiments/2026-08-09g-decompose-diversity-regression.md`
  修正後 → `experiments/2026-08-09h-decompose-diversity-merge-protect.md`
  （multihop 54% → 73%、比較可能な45問中の regression 4件のうち3件を回復）

## 背景

`0010`（クエリ分解）・`0011`（記事多様化）を入れて `npm run eval` を agentic のみで
実行したところ、multihop の完全ヒット率が (f) の 65〜68% から **54%** まで悪化した。
raw ログを突き合わせると、**4問が「(f)では正解 → 導入後は不正解」に転落し、
正味の改善は確認できなかった**（比較可能な45問中）。

## 原因の特定

「Amazon Bedrock/Cognito」の質問（golden: 2記事にまたがる2チャンク）で再現した。

- **(f)（分解なし）**: 元の質問1本で検索 → **両方の golden chunk が上位5件に入り正解**
- **導入後（分解あり）**: 元の質問 + サブクエリ2本を検索し、`mergeHits` で
  **生スコアを跨いで統合**・上位8件に切る → サブクエリ側が拾った**別の（不正解の）候補**が
  正解の一方を押し出し、不正解に転落

`0009` が既に指摘していた「エージェント自作の言い換えクエリは元の質問より検索性能が低い」
という現象が、分解の副産物としてもう一度出た。分解のサブクエリは「対象を絞っただけの
忠実な言い換え」のつもりだったが、それでも言い換えは言い換えであり、
**この質問では既に元の質問1本で両対象を正しく引けていた**。

`mergeHits` が異なるクエリの RRF スコアをそのまま比較可能とみなしていたのが根本原因。
狭いサブクエリはその狭い母集団内で相対的に高いスコアを出しやすく、
質問全体を捉えた主クエリの正解候補より上位に来てしまうことがある。

## 決定

**主クエリ（元の質問）の上位候補は無条件に残し、補助クエリ（分解・多様化）の候補は
主クエリと重複しない chunk_id を、スコアで競合させずに追加枠として足す。**

```
主クエリ（元の質問）の上位 SEARCH_K 件 → そのまま確定
  + 補助クエリ（分解のサブクエリ／多様化の別記事検索）の候補のうち
    主クエリに含まれない chunk_id を、最大 MAX_SUPPLEMENTARY(4) 件まで追加
```

`0010`/`0011` で「見せる候補数は SEARCH_K のまま据え置く」としていた制約は撤回する。
結果的に分解・多様化が発火した質問だけ候補数が SEARCH_K〜SEARCH_K+4 件に増える。
これは意図的なトレードオフ——**候補数を固定して主クエリの正解を犠牲にするより、
候補を数件増やしてでも主クエリの実績を守る方を優先した**。発火しない質問（大半)は
影響を受けない（主クエリ8件のみ、従来と同一）。

### なぜ `MAX_SUPPLEMENTARY = 4` か

仮の値。SEARCH_K(8) の半分。増やしすぎるとエージェントに見せるプロンプトが
再び肥大化する（トークンコストは既に単発の25倍という背景がある）。
効果を見ながら調整する。

## 副作用として受け入れたこと

- 分解・多様化が発火した質問は、発火しなかった質問よりプロンプトがわずかに長くなる
  （候補数が最大12件になりうる）。パターン1・2との比較で「見せる量」を厳密に揃える
  という当初の制約は緩めたことになる。ただし発火は質問の性質に依存し恣意的な
  水増しではないため、比較の妥当性を損なうものではないと判断した。

## 検討した代替案: RRFによる複数クエリ統合（未実装）

`mergeProtectingPrimary` は「主クエリを無条件優先する」という非対称なルールで
regression を止めた場当たり的な修正であり、より原理的な代替案を検討した。

**複数クエリ（主クエリ＋補助クエリ）の結果リストを、生スコアではなく順位ベースの
RRF（Reciprocal Rank Fusion）で統合する。** LanceDB の `RRFReranker` は
BM25とベクトルという2系統の結果をRRFで融合しているが、今回の regression は
「クエリが違う複数の結果リストを融合する」という、実質的に同じ問題を
生スコアの比較で解こうとして起きた。同じ考え方（順位は異なるクエリ間でも
比較可能な指標だが、スコアは比較できない）を複数クエリ間の統合にも適用すれば、
主クエリを特別扱いするルールを持ち込まなくても、正解候補が不当に押し出される
問題は原理的に起きにくかった可能性がある。

これを試さなかった理由は単純にコスト（追加の実装・評価にかかる時間とAPI費用）で、
「効果があるかどうか」ではない。`0005` が見送った Cross-Encoder リランクとは別物
（RRFは順位の統計的融合であって意味的な再スコアリングではない）だが、
`0005` の「将来リランクを入れる場合の条件」の2番目
（*ループの改善が実質的に順位の入れ替えでしかない*）に近い状況が
今回のregressionで観測されたとも言え、`0005` に追記した。

試すなら、`dedupeByScore`（現在は生スコアで統合）を、chunk_id ごとに
「各クエリでの順位」を集計してRRF式 `Σ 1/(k + rank)` でスコアを再計算する
関数に置き換える形になる。`mergeProtectingPrimary` と比べて実装はやや複雑になるが、
`MAX_SUPPLEMENTARY` のような仮の閾値を置かずに済む可能性がある。

## 検証結果

小規模検証（regression した4問 + (f)で負けていた5問、計9問）: 4/9 正解。
regression した4問中3問（Amazon Bedrock/Cognito・Docker Compose Qwen3・
H200 tensor-parallel）が回復し、既存の正解問題を壊していないことも
スモークテスト（維持率10/10）で確認した。その後 `npm run eval` を
agentic のみで再実行し、multihop 完全ヒット率が 54% → **73%**
（(f)の65〜68%からも上昇）まで回復・改善したことを確認した
（`experiments/2026-08-09h-decompose-diversity-merge-protect.md`）。

## 教訓

複数クエリの検索結果を統合する際、**異なるクエリ間のスコアを直接比較して競合させない**。
スコアは同一クエリ内の相対順位としてのみ信頼できる。統合するなら
「主/補助」のような非対称な役割を与え、実績のある候補を無条件で守る設計にすること。

# 0008. 充足チェックを回答生成の「前」に置く

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/workflows/agentic-rag/evidence-check.ts`, `confidence-check.ts`
- 実測: `experiments/2026-08-08b-budget-aware.md`

## 背景

architecture.md の初期設計では、確信度チェック（FLARE 的な事後補正）を
**回答生成の後**に置いていた。

```
検索スキル（search→fetch ループ）→ 回答生成 → 確信度チェック →（不確実なら追加検索へ戻る）
```

## 問題: ループがほとんど働かなかった

実験(a)(b) で、パターン3のターン数の**中央値が 1**、46問中25問が1回の検索で完結した。
再検索という機能が事実上使われていない。

原因は2つある。

1. エージェント自身が1回目の検索結果で「十分」と判断してループを抜ける
2. **回答生成後のチェックは、すでに書かれた回答文を見て判定する**

2 が効いていた。一度回答文が生成されると、その**流暢さが根拠の不足を覆い隠す**。
根拠が片方の文書しかなくても、文章としては尤もらしく仕上がるため
「十分」と判定されやすい。

multihop 質問（複数文書の統合が必要）では特に問題になる。
「もう片方の文書が足りない」と言えるのは、回答文ではなく**根拠そのもの**を
見ているときだけである。

## 決定

**根拠の充足チェックを回答生成の前、収集段階に置く。**

```
検索スキル
  ├─ search→fetch ループ
  ├─ 充足チェック（根拠のみを見る。回答文は渡さない）
  └─ 不足なら「何が足りないか」を添えて再収集（最大3ラウンド）
→ 回答生成
→ 確信度チェック（役割を縮小、再突入は1回まで）
```

判定器には**回答文を渡さない**。渡すと元の問題が再発する。
質問と、集まった根拠と、これまでに試したクエリだけを渡す。

## 2つのチェックの役割分担

事後の確信度チェックは削除せず、守備範囲を絞って残した。

| チェック | 位置 | 捉える失敗 |
|---|---|---|
| 充足チェック | 回答生成の**前** | **根拠が足りない**（＝検索し直すべき） |
| 確信度チェック | 回答生成の**後** | 根拠は足りているのに**回答がそれを正しく使えていない** |

後者は前者では原理的に検出できない（回答文がまだ存在しないため）ので、
両方を独立した安全装置として残すのが妥当と判断した。
ただし守備範囲が狭くなったぶん、再突入の上限は 2 → 1 に減らしている。

## 不足の内容をエージェントに渡す

充足チェックは `missing`（何が足りないか）と `followup_query` を返し、
それを次ラウンドの search/fetch ループにプロンプトとして渡す。

不足が具体的に分かるほどクエリの言い換えが的確になる。
「もう一度探して」だけでは同じクエリを繰り返しやすい。

## 検証

修正前に multihop で失敗していた質問での動作確認:

> 「LLaVAはLLMの学習段階のうち何を画像に対して実施しており、LLaVA-Medは医療画像を用いて
> どのような2段階の学習を行うことで医療画像チャットモデルを構築していますか？」

- 修正前: 1ターン、根拠3件、不正解
- 修正後: **2ターン、根拠5件（予算を使い切り）、LLaVA と LLaVA-Med の両記事から取得して正解**

充足チェックが2ラウンド目を発火させ、クエリが
「LLaVA 学習段階 画像 …」→「LLaVA 学習 画像に対する instruction tuning 視覚的指示チューニング 2段階 projection weights pretraining」
と具体化している。

## 副作用として受け入れたこと

チェックが1回増えるぶん、パターン3のトークン消費とレイテンシはさらに増える。
もともと単発ハイブリッドの約20倍を使っている構成なので、
**エージェント化の損益分岐はさらに悪化する方向**である。

それでも入れる判断をしたのは、ループが働かないままではエージェント的RAGの効果を
測ること自体ができず、比較実験が成立しないため。
コストの評価は精度の差が観測できるようになってから行う。

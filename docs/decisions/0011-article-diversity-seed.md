# 0011. 種検索の記事多様化

- ステータス: 採択
- 日付: 2026-08-09
- 関連: `src/search/hybrid-search.ts`, `src/workflows/agentic-rag/search-fetch-loop.ts`
- 実測: `experiments/2026-08-09g-decompose-diversity-regression.md`（初回はマージ方式の
  設計ミスで regression）→ `experiments/2026-08-09h-decompose-diversity-merge-protect.md`
  （`0012` で修正後、multihop 65〜68% → 73%）

## 背景

`0010` でクエリ分解を入れたが、対象を絞った動作確認（(f) で単発ハイブリッドに負けた5問の
再実行）で、5問中4問は分解が発火しないまま従来と同じ結果に終わった。

原因を `evals/generate-multihop-set.ts` で確認すると、multihop 質問は生成時点で
**「自己完結した自然な1文」になるよう意図的に作られている**（`is_natural` 判定で
強引な接続を弾いている）。つまり質問の表層構造から「2記事にまたがる」ことを
読み取れないケースが多く、`0010` の分解（表層の対象分離）では原理的に対応できない。

負けている質問を個別に見ると、共通するパターンは
**「上位候補が1記事に偏り、エージェントが最後までもう一方の記事の存在に気づかない」**
というものだった。これは質問の書き方の問題ではなく、種検索の候補プールが
記事多様性を欠いているという検索側の問題である。

## 決定

**種検索の上位候補が単一記事に偏っている場合、その記事を除外して追加検索し、
候補プールに別記事の候補を混ぜる。**

```
種検索（元の質問）→ 上位5件の article_id を見る
  ├─ 複数記事が混在 → そのまま（何もしない）
  └─ 1記事に偏っている → その記事を除外して再検索 → chunk_id で統合（max score）→ 上位 SEARCH_K 件
```

`hybridSearch` に `excludeArticleIds` オプションを追加し、LanceDB の `where()` で
`article_id NOT IN (...)` を掛ける。同じ手口を golden set 生成側
（`generate-multihop-set.ts` の近傍抽出）が既に使っており、対応が取れている。

### なぜ `0010` の分解と独立した仕組みにしたか

分解は「質問の表層構造」に基づく多様化、多様化（本ADR）は「検索結果の記事構成」に
基づく多様化で、見ている対象が違う。分解が発火しない（表層に対象分離のヒントがない）
質問にもこちらは効く。両方が同時に発火してもよい設計にしてあるが、実装上は
分解が発火した場合（`subQueries.length > 0`）は分解側のマージ結果をそのまま使い、
多様化はスキップする——分解が既に複数クエリで記事をまたいでいる可能性が高く、
二重に判定する必要が薄いため。

### なぜLLM呼び出しを増やさないか

判定は「上位5件の article_id を数える」だけなので、LLMを使わない。
`0009`〜`0010` の一連の変更点はすべて根拠の充足チェック・確信度チェック・分解判定と
LLM呼び出しを積み増す方向だったため、コスト増を伴わずに効く手があるなら
そちらを優先する。実際に増えるコストはハイブリッド検索（LanceDBクエリ）1回分のみで、
埋め込みAPI呼び出し1回とDB検索が追加されるが、生成トークンには影響しない。

### なぜ候補数は SEARCH_K のまま据え置くか

`0010` と同じ理由。見せる候補の量を固定し、変数を「候補の中身」だけに絞る。

### なぜ search ツールの残り予算（MAX_TURNS）を削らないか

`0010` と同じ理由。多様化はエージェント自身の判断ではなく前処理であり、
種検索全体を「1ターン目」として扱う。

### queryTrace への記録

多様化が発火した場合、`"{question}（記事 {id} を除外）"` という形で `queryTrace` に追加する。
実際に発行した検索回数を隠さない、という `0010` の方針を踏襲。

## 副作用として受け入れたこと

- 上位5件がたまたま1記事に偏っているだけの easy 質問（本来1記事で完結する質問）でも
  多様化が誤発火し、無関係な記事の候補が候補プールに混ざる可能性がある。
  **実測（`experiments/2026-08-09h-*.md`）で確認: easy はヒット率こそ (f) と同じ95%で
  精度への実害はなかったが、レイテンシ +56%・入力トークン +22% という無駄なコストが
  そのまま乗っていた。** easy 質問は単一記事・単一トピックという golden set の設計上、
  上位5件がほぼ必ず1記事に偏るため、多様化がほぼ毎回誤発火している。
  難易度を判定できない以上ここを狙って抑制する手段は今のところないが、
  次にコストを詰めるならこの誤発火率が対象になる。
- 判定基準（上位5件・1記事のみなら発火）は仮の値のまま。厳しすぎる/緩すぎるかの
  感度分析はまだ行っていない。

## 未検証のまま残したこと

- 分散を測っていない（既存の課題と同じ）。
- 「上位5件」という閾値の感度分析はしていない。
- 3記事以上にまたがる質問には未対応（現在の golden set は2記事構成のみなので対象外）。

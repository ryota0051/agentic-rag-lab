# 0010. 複合質問のクエリ分解を種検索に導入する

- ステータス: 採択
- 日付: 2026-08-09
- 関連: `src/workflows/agentic-rag/query-decompose.ts`, `search-fetch-loop.ts`
- 実測: `experiments/2026-08-09g-decompose-diversity-regression.md`（初回はマージ方式の
  設計ミスで regression）→ `experiments/2026-08-09h-decompose-diversity-merge-protect.md`
  （`0012` で修正後、multihop 65〜68% → 73%）

## 背景

`0009` の診断と `experiments/2026-08-09f-snippet-500.md` までの一連の実験で、
実装・計測のバグを潰した後もパターン3が単発ハイブリッドに負ける原因が2つに絞られていた。

1. 損失A（クエリ言い換え） → 1ターン目を元の質問固定にすることで解消済み（`0009`）
2. 損失B（見えていたのに fetch しなかった） → スニペット厚化で 7件→4件まで改善（(f)）

(f) で残った損失Bの4件・単発ハイブリッドに負けた5件は、いずれも
「AではX、BではYですか」「AとBの違いは」のように**独立した2つの対象**を
1文に含む質問に偏っていた。これは同じ対象の言い換えでは解けない。
`0009` が禁じた「語を継ぎ足す」言い換えと、対象を分けて別クエリにする分解は別の操作であり、
既存の言い換え指示（search-fetch-loop.ts のエージェント指示）に混ぜると
「対象を1つに絞った短いクエリにする」という指示と役割が衝突する。

## 決定

**質問分解を独立したステップとして切り出し、収集1ラウンド目の種検索でのみ使う。**

```
質問 → 分解判定（is_compound? → sub_queries 最大2件）
  ├─ 複合でない → 従来通り、元の質問1本で種検索
  └─ 複合        → 元の質問 + sub_queries を並行に種検索 → chunk_id で統合（max score）→ 上位 SEARCH_K 件
```

### なぜ独立ステップか（skill-select に混ぜない）

skill-select の責務は「search/direct のどちらか」に絞られている（`0001`）。
分解要否の判定をそこに混ぜると、100%を維持している skill-selection-accuracy を
道連れにするリスクがある。1LLM呼び出し分のコストを払ってでも分離する。

### なぜ2ラウンド目以降・確信度チェックの追加検索では使わないか

分解は「元の質問が複数対象を含むか」を見る操作であり、2ラウンド目以降の
`missingHint` は既に対象が絞られた不足情報（例:「B側の起動オプションが未確認」）である。
これを分解しても同じクエリを繰り返すだけで、無駄なLLM呼び出しになる。

### なぜ候補数を SEARCH_K のまま据え置くか

分解で複数クエリを検索しても、エージェントに見せる候補リストは
従来と同じ `SEARCH_K`（8件）に絞る。ここを増やすと「候補が多いから見つかった」のか
「分解で的確な候補が上位に来たから見つかった」のかが交絡する。
変数を分解の効果1つに絞るため、見せる量は固定する。

### なぜ search ツールの残り予算（MAX_TURNS）を削らないか

分解による複数クエリの種検索は、エージェント自身の判断ではなく前処理として行う。
1回のハイブリッド検索を種にしていた従来動作と同様、種検索全体を「1ターン目」として
`counter.searchCalls` を1しか進めない。これにより、分解を使っても
エージェント自身が追加で言い換え検索できる残り回数は変わらない
（`MAX_TURNS=3` のうち従来通り2回分が残る）。

一方 `turns`（レポート上のターン数統計）には分解で増えた検索回数をそのまま反映する。
LanceDB へのクエリ自体は安価だが、実際に発行した検索回数を隠すと
コスト比較が歪むため、予算消費と統計上の可視性は別物として扱う。

## 副作用として受け入れたこと

- 複合質問かどうかに関わらず、検索スキルが選ばれた質問には毎回1LLM呼び出し
  （分解判定）が増える。easy 問題（単一対象が大半）でも分解判定自体は走るため、
  「複合でない」という判定結果を得るためだけのコストが乗る。
  既存の評価スチェック（evidence-check / confidence-check）も同様に無条件で
  毎回走らせている設計との一貫性を優先し、ヒューリスティックな事前フィルタは入れない。
- もともと単発ハイブリッドの約25倍のトークンを使っている構成なので、
  損益分岐はさらに悪化する方向。効果が出なければ「決定点をまた1つ増やしただけ」で
  ADR 0009 の教訓通りの結果になりうる。次の `npm run eval` で easy / multihop 双方を
  再測定し、多い/少ないの結果に関わらず experiments/ に記録すること。

## 未検証のまま残したこと

- 分散を測っていない（既存の課題と同じ）。1回の実行で語れるのは方向のみ。
- 対象を3つ以上含む質問（今回は最大2分割に制限）。
- 分解クエリの統合を単純な max-score マージにしている。RRFのような順位ベース融合の方が
  良いかは比較していない。

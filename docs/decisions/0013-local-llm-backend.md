# 0013. 生成・エージェントLLMをローカルに差し替えられるようにする

- 状態: 採用
- 日付: 2026-08-16

## 背景

これまでの実験は3パターンすべてを OpenAI `gpt-5.6-luna` で回してきた。
そこで観測できるのは「検索戦略とループの有無」による差だけで、
**エージェント的RAGの成立にモデルの能力がどれだけ効いているか**は分離できていない。

エージェント的RAGはモデルに対して、単なる文章生成より強い要求をしている:

- `search` / `fetch` のツールを正しい引数で呼ぶ
- `fetch` の `scope` を選ぶ（どこまで広げて読むかを自分で決める）
- 検索回数の予算を守る
- スキル選択・充足チェック・確信度チェック・質問分解でスキーマ通りのJSONを返す

これらが崩れたときに何が起きるかを見るため、
**生成・エージェントのLLMだけを変数にした比較軸**を追加する。

## 決定

`LLM_BACKEND` 環境変数（`openai` 既定 / `local`）で生成・エージェントのモデルを切り替える。
定義は従来どおり `src/shared/llm-client.ts` の1箇所に閉じ込める（CLAUDE.md の不変条件2）。

Mastra の `MastraModelConfig` は model router の文字列に加えて OpenAI 互換エンドポイントの
設定オブジェクト（`{ id, url, apiKey }`）も受け付けるため、分岐はこのファイルだけで済んだ。
ワークフロー側は一切変更していない。

ローカルモデルは **Qwen3.8-27B（unsloth GGUF, UD-Q4_K_XL）** を
**llama.cpp の公式Dockerイメージ**で OpenAI 互換サーバとしてホストする。

### 埋め込みと judge は OpenAI のまま固定する

- **埋め込み**: `text-embedding-3-large` のまま。LanceDBインデックスも作り直さない。
  検索側を固定することで、変数がエージェントを駆動するLLM1つだけになる
  （不変条件1・3をそのまま維持できる）。
- **judge**: `JUDGE_MODEL` もクラウドのまま。golden set はこのモデルで生成されており、
  判定側まで差し替えると**ものさし自体が変わって**過去の実験レポートと比較できなくなる。

つまり `LLM_BACKEND=local` でも `OPENAI_API_KEY` は引き続き必要。

## ランタイムの選定

### vLLM を採らなかった理由

unsloth が案内する vLLM 経路は `unsloth/Qwen3.8-27B-NVFP4` を前提にしている。
NVFP4 は Blackwell 世代のハードウェア機能で、検証機の **RTX 4090 は Ada 世代**のため使えない。
検討の余地なく除外。

### Ollama を採らなかった理由

Ollama は導入済みで最も手数が少なかったが、サンプラーと
`chat_template_kwargs`（`reasoning_effort`）の指定が Modelfile 経由の間接的なものになる。
今回は**思考モードを実験条件として固定したい**ので、条件を直接フラグで書けることを優先した。

### llama.cpp を Docker で動かす理由

ビルド済みWindowsバイナリでも動くが、CUDAランタイムDLLが別配布で、
展開手順を誤ると起動時に落ちる。それ以上に重要なのは再現性で、
**イメージタグを固定すれば実行環境ごと再現できる**。

実験リポジトリとして、これは「どのフラグで回したか」と同格の記録である。
`docker/compose.yaml` はタグを `server-cuda-b10450` に固定してあり、
floating な `:server-cuda` は使わない。

### サーバ設定の要点

- `--jinja` … **必須**。付けないとモデル同梱のチャットテンプレートが使われず、
  tool call が解釈されない（この実験の主題そのものが成立しなくなる）
- `--chat-template-kwargs '{"reasoning_effort":"none"}'` … 思考モードの固定。理由は次節
- `--cache-type-k q8_0 --cache-type-v q8_0` … 24GB に約18GBのモデルを載せた残りで
  KVキャッシュを賄うため量子化が必要
- Compose の `command` は**リスト形式**で書く。文字列形式だと Compose が shlex で分割し、
  `--chat-template-kwargs` に渡すJSONのクォートが剥がされて不正なJSONになる

## reasoning_effort を none に固定する理由

Qwen3.8 は `xhigh` / `medium` / `low` / `none` を選べる。思考を有効にすると
出力トークンとレイテンシがそれに支配され、**ツール使用の変化が数値に埋もれる**。

今回見たいのは「ツールをどう使うか」なので、まず思考を切った条件で比較する。
`reasoning_effort` 自体を実験軸にするのは、この軸で差が出ることを確認してからでよい。

## ツール使用の計測を先に入れる（重要）

**この判断がこのADRの本体である。**

ローカルモデルがツール呼び出しや構造化出力に失敗しても、既存のコードでは
フォールバックが働いて**もっともらしい正常値**に化けてしまう:

| 箇所 | 失敗時のフォールバック | 結果として見えるもの |
|---|---|---|
| `skill-select.ts` | `"search"` を選ぶ | 「正しく検索を選んだ」 |
| `evidence-check.ts` | `sufficient=true` | 「1回で足りた」＝ループ不要 |
| `confidence-check.ts` | `sufficient=true` | 「追加検索は不要だった」 |
| `query-decompose.ts` | 空配列 | 「複合質問ではなかった」 |
| `fetch.ts` | 未知の `chunk_id` を黙って捨てる | 掴んだ事実自体が消える |

これらは個別には妥当な設計（判定失敗で無限ループさせないため）だが、
**モデルを差し替える実験では致命的**になる。ツールを使えていない状態が
「ターン数中央値1、ループが働かなかった」という**もっともらしい嘘の観測**に化け、
バグを実験結果として記録してしまう。

そこで `ToolUseStats`（`src/shared/types.ts`）を追加し、失敗を明示的に数える:

- `searchToolCalls` / `fetchToolCalls` … 実際の呼び出し回数
- `searchBlockedCalls` … 回数上限を超えて呼びに来た回数（指示追従性）
- `fetchScopes` … `chunk_only` / `with_neighbors` / `whole_section` の内訳。
  「読む範囲を自分で決める」という [0003](0003-search-fetch-separation.md) の狙いが
  機能しているかの直接指標
- `fetchNoOpCalls` … 取得済みIDの再要求（同じ行動の反復）
- `fetchUnresolvedIds` … 本文が返らなかったID数。**存在しないIDと予算切れの合算**であり、
  「ハルシネーションID数」と断定してはいけない
- `structuredOutputFailures` … 4箇所の構造化出力の失敗回数

カウントは**ツール実装の内側**で行う。LLMの応答テキストから推測すると、
ツールを呼ばずに「呼びました」と書くモデルを通してしまい、検出したい失敗モードを取り逃がす。

`structuredOutputFailures` が0でない実験結果は、ターン数分布もスキル選択精度も
「モデルの判断」ではなく「フォールバックの結果」を測っている。
レポート生成側（`evals/run-comparison.ts`）はこの場合に警告文を自動で差し込む。

## 事前チェックを必須にする

`npm run verify-local-llm` で「素の生成 / ツール呼び出し / 構造化出力」を個別に確認する。

ローカルの比較実験は1回が長時間になる。その最後に「実はツール呼び出しが一度も
成立していなかった」と分かるのが最悪の失敗であり、しかも上記のフォールバックのせいで
結果は一見まともに見える。本番実行の前に必ず通すこと。

ツール呼び出しの判定は**ツールの `execute` が実際に走ったか**で行う。
応答テキストで判定すると、呼ばずに「呼びました」と書くモデルを通してしまう。

## 結果

- 検索側（ingestion・チャンク分割・埋め込み・ハイブリッド検索）は一切変更していない
- 3パターンは引き続き同一インデックス・同一プロンプト・同一 k=5 を共有する
- `RagRunResult` に増えたのは `toolUse?` のみ。`selectedSkill?` / `queryTrace?` と同じ
  パターン3専用オプショナルで、不変条件5の「同一形状」は保たれている
- `<think>` の除去は3パターン共通の `src/shared/generate.ts` に置いた。
  どれか1つのワークフローだけに入れると「回答の後処理がパターンによって違う」状態になり、
  比較実験が無効になる（不変条件2）

## 副次的な修正

- `GENERATION_MODEL` がオブジェクトを取りうるようになったため、レポート表示用に
  `GENERATION_MODEL_LABEL` を追加した。従来のテンプレートリテラル直挿しは
  ローカル時に `[object Object]` を出力してしまう
- 実験レポートと生ログのファイル名にバックエンド・難易度由来のスラグを入れた。
  固定名のままだと同じ日にクラウド版とローカル版を回したときに互いを上書きし、
  「1実験1ファイル」の約束が壊れる

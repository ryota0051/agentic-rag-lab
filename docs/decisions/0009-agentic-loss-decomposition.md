# 0009. エージェント的RAGが単発検索に負ける原因の切り分け

- ステータス: 採択
- 日付: 2026-08-09
- 関連: `evals/diagnose-agentic.ts`, `src/workflows/agentic-rag/search-fetch-loop.ts`
- 実測: `experiments/2026-08-08b-budget-aware.md`

## 背景

実験(a)〜(d) を通じて、エージェント的RAG（パターン3）が単発ハイブリッド検索（パターン2）に
一貫して負けていた。「エージェント化はコストが増えるだけ」という結論を出す前に、
**どこで負けているのか**を測った。

## 診断方法

エージェントは実際に投げたクエリを `queryTrace` に残している。これを使い、
損失を3段階に分解した（生成は走らせず埋め込みのみ、数十秒・ほぼ無料）。

`evals/diagnose-agentic.ts`（`npm run diagnose`）

## 結果（実験(b) の agentic 46件）

| 段階 | 完全ヒット |
|---|---|
| ① 元の質問そのまま @5（＝パターン2と同条件） | **37/46 (80%)** |
| ② エージェントの言い換えクエリ @5 | 29/46 (63%) |
| ③ 同 @8（エージェントが実際に見た候補） | 35/46 (76%) |
| ④ 実際に fetch した根拠（最終結果） | **31/46 (67%)** |

損失は2箇所で起きていた。

### 損失1: クエリ言い換えが検索を劣化させる（①→②で -17ポイント）

エージェントは元の質問を捨て、同義語・関連語を**継ぎ足した**クエリを作っていた。

> 元:「vLLMのmax-model-lenを小さくすると速度が改善するのはなぜ？」
> 言い換え:「vLLM max-model-len を小さくすると推論速度が改善する理由 KV cache メモリ 使用量 スケジューリング 長いコンテキスト」

語の水増しは BM25 では一致度を薄め、ベクトルでは「質問文の意味」を「語の羅列」に変質させる。
top-8 まで見ることで76%まで回復しているが、**言い換えは正味マイナス**だった。

「クエリ整形は検索を良くする」という前提（architecture.md の初期設計）は、
この構成では成立していなかった。

### 損失2: 200字のスニペットだけで選ばせている（③→④で 7件）

候補リストに正解が見えていたのに fetch しなかったケースが7件。順位を調べると:

```
正解chunkの順位:      1, 2, 3, 6, 6, 6, 6
そのとき取得した件数: 1, 1, 5, 3, 3, 5, 5
```

**3件は1〜3位に表示されていたのに取っていない**（うち2件は1件だけ取って打ち切り）。
search が本文を返さない設計（`0003`）の裏返しで、エージェントは200字で
「読む価値があるか」を判断させられている。判断材料が薄すぎた。

## 構造的な理解

単発ハイブリッドは**判断を一切しない**。生の質問を投げ、上位5件を機械的に渡す。決定点ゼロ。

エージェント的RAGは決定点を4つ持つ（クエリ書き換え / 候補の取捨選択 / 読む範囲 / 十分性判定）。
**そのすべてが情報を失いうる箇所**であり、今回の実装では正味の損失になっていた。

エージェント化が報われるのは、この損失を上回る利得——単発では原理的に届かない根拠を
複数回の検索で取りに行くこと——が出るときだけである。

## 決定

### 1. 1ターン目は元の質問をそのまま使う（コードで保証）

エージェントに「元の質問を使え」と指示するのではなく、**1ターン目の検索をコード側で実行**し、
その結果を渡した状態からエージェントを開始する。言い換えは「1回目で足りなかったとき」の
手段として2ターン目以降に回す。

これで最低でも ①80% の地点から始められる。
architecture.md の「1ターン目は必ずハイブリッド検索を通す」というガイドとも一致する。

### 2. 言い換えは「足す」ではなく「置き換える」

ツールの description と指示を書き換え、
- 語を継ぎ足して長くしない（**検索精度が下がる**理由を明記）
- 元の質問と同じ長さかそれ以下の、別の言い方の文にする
- 略語⇄正式名称、質問の言葉→文書側で使われていそうな言葉
- 複数対象を含む質問は、対象を1つに絞った短いクエリにする

## 診断中に見つかった計測バグ

**`retrieved_chunk_ids` が fetch の seed だけを記録していた。**

`with_neighbors` / `whole_section` で範囲拡張すると、実際には複数チャンクが本文として
結合されてプロンプトに入る（`FetchResult.included_chunk_ids`）。しかし採点対象には
seed の chunk_id しか入れていなかった。

範囲拡張はパターン3だけが使う機能なので、**エージェント側だけを一方的に減点していた**。
実例として「データ拡張手法をすべて挙げよ」という質問で、回答内容は完全に正解なのに
seed が `#4`・正解が `#3` のため不正解と採点されていた。

`src/shared/evidence-stats.ts` に集約し、3パターンとも
`collectRetrievedChunkIds()`（結合されたチャンクをすべて含む）を通すよう修正した。

ただしこれにより、パターン3は1件の根拠に複数チャンクを含められるぶん
**情報量で有利**になりうる。件数だけ見ると誤解を招くので、
レポートに `平均根拠文字数` を併記して情報量の非対称を可視化した。

## 教訓

比較実験では、**片方のパターンだけが使う機能が採点対象から漏れていないか**を疑うこと。
今回は「範囲拡張」というパターン3固有の機能が、そのまま減点要因になっていた。

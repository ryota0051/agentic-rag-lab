# 0001. 検索要否の判定をスキル選択に一本化する

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/skills/descriptions.ts`, `src/workflows/agentic-rag/skill-select.ts`

## 背景

エージェント的RAGでは「この質問に検索が必要か」を判断する必要がある。
素直に組むと、フローは次のようになる。

```
質問 → 検索要否の判定 → (必要なら) スキル選択 → 実行
```

## 決定

検索要否の判定を独立したステップとして持たず、**スキル選択そのものに判定を兼ねさせる**。
直接回答も1つのスキルとして候補に含める。

```
質問 → スキル選択（直接回答スキル / 検索スキル）→ 実行
```

判定ロジックはコードに書かず、2つのスキルの **description（トリガー条件）に集約**する。

## 理由

- 検索要否判定とスキル選択のトリガー判定は、実質的に同じ判断をしている。
  分けると同じ判断を二重に行うことになり冗長
- スキル選択のプロセス（description と質問のマッチング）自体が、
  「ツールを呼ぶかどうか」＝検索要否の判定を自然に兼ねる
- マッチするスキルがなければ直接回答スキルにフォールバックする形になり、
  「検索なしで答える」ケースも同じ選択メカニズムの中で説明できる
- 判定基準が description という**1箇所のテキスト**に集まるため、
  評価して改善する対象がはっきりする

## 検索要否は完璧には判定できない、という前提

LLM が自身の知識境界を正確に自己申告することは原理的に困難である（calibration 問題）。
したがって**完璧な事前判定を目指さない**。代わりに「間違えたときのコストが小さくなるように
設計する」方針を取る。

失敗のコストは非対称である。

- **検索すべきなのに直接回答した**（取りこぼし）→ 誤った情報を自信をもって答える。**高コスト**
- **検索不要なのに検索した**（過剰発火）→ レイテンシとトークンが余分にかかるだけ。**低コスト**

そこで description を両側から検索側へバイアスさせた。

1. 検索スキル側に「判断に迷う場合は、直接回答ではなくこちらを優先する」
2. 直接回答側に「文書に存在しうる情報が少しでも含まれる場合はこのスキルを使わず、
   検索スキルに委ねること」
3. **否定条件は直接回答側にのみ書く** — 判定の揺れを常に検索側に吸収させる

さらに、事前判定の取りこぼしをリカバーする保険として、生成後に確信度チェックを置いた
（`confidence-check.ts`）。

## 評価方法

この設計が意図通り機能しているかは、`evals/boundary-cases.json` に対する
**検索スキルの Precision / Recall** で測る（`evals/scorers/skill-selection-accuracy.ts`）。

単なる正解率では非対称性が見えなくなる。設計が効いていれば
**Recall が高く、Precision はそれより低い**形になるはず。
Precision の方が高いなら、description が保守的すぎて検索に倒せていないことを意味する。

## 帰結

- description は日本語で統一した。ユーザーの質問文と同じ言語空間で判断させることで、
  専門用語・固有名詞の表層一致という手がかりを活かせる
- description を変更したら skill-selection-accuracy を測り直すこと。ここは実験対象そのもの
- スキル選択は structured output で返させる。自由文で返させると
  「どちらが選ばれたか」の集計が不安定になり、採点できない

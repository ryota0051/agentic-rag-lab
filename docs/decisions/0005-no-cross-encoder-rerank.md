# 0005. Cross-Encoder によるリランクを今回は導入しない

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/search/hybrid-search.ts`, `docs/comparison-experiment.md`

## 背景

当初の設計（architecture.md 初版）では、検索を3段構えにする想定だった。

1. BM25 + ベクトルのハイブリッド検索で候補を広め（top20程度）に取る
2. Cross-Encoder で精密に再スコアリングして top5 に絞る
3. fetch で本文を取得

これは検索精度としては妥当な構成である。スコアのスケールが揃わない問題を、
単純な線形結合よりも確実に回避できる。

## 決定

**Cross-Encoder リランクは今回は入れない。** 比較実験は以下の3パターンとする。

1. ナイーブRAG（ベクトル top-k・単発）
2. **ハイブリッド検索（BM25 + ベクトル、RRF融合）・単発**
3. エージェント的RAG（スキル選択 + search/fetch ループ）

## 理由

このプロジェクトの主題は「**普通のRAGとエージェント的RAGは何が違うのか**」であり、
検索器そのものの精度を上げることではない。

リランクを入れると、パターン2が「ハイブリッド＋リランク」になり、パターン3との差分が
「ループの有無」と「リランクの有無」の**2変数**になる。パターン3で改善が見られたとき、
それがエージェント化の効果なのかリランクの効果なのかを切り分けられない。

変数を1つに保つため、パターン2とパターン3は**同一の検索器（ハイブリッド検索）を共有**し、
差分をループの有無だけに限定した。

## RRF は「リランク」ではない（重要な区別）

LanceDB のハイブリッド検索は、BM25 の結果集合とベクトル検索の結果集合を融合する
ステップを**必ず要求**する。既定は `RRFReranker`（Reciprocal Rank Fusion）である。

名前に "Reranker" が付くため紛らわしいが、RRF は**順位の統計的な融合**であって、
クエリと文書の組を読み直して意味的にスコアし直す Cross-Encoder とは別物である。
本 ADR が見送ったのは後者であり、RRF 融合はハイブリッド検索の必須構成要素として
そのまま使っている。

## 帰結

- ディレクトリ構成から `src/search/rerank.ts` を削除した
- パターン2のワークフローは `hybrid-rerank.ts` ではなく `hybrid-rag.ts` とした
- 埋め込みは OpenAI に統一したため、リランカーAPI（Voyage 等）への依存も消えた。
  必要な API キーは `OPENAI_API_KEY` のみになり、セットアップが単純になった

## 将来リランクを入れる場合の条件

以下のいずれかが観測されたら再検討する。

- パターン2の retrieval-recall が低く、かつ**正解チャンクは top-20 には入っている**
  （＝候補は取れているが順位付けが悪い）。これはリランクが効く典型的な状況
- パターン3がループで改善している内容が、実質的に「順位の入れ替え」でしかない
  （＝エージェントに何度も検索させる代わりにリランクで済む）

導入する場合は**4番目のパターンとして追加**し、パターン2を書き換えないこと。
書き換えると過去の実験ログと比較できなくなる。

# 0007. 日本語全文検索のトークナイザに `icu` を採用する

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/index/build-index.ts` (`FTS_TOKENIZER`), `src/index/verify-fts.ts`

## 背景

パターン2（ハイブリッド検索）とパターン3（エージェント的RAG）は、BM25による
キーワード一致に依存している。専門用語・固有名詞の完全一致を担うのがBM25の役割であり、
ここが機能しないとハイブリッド検索は実質ベクトル検索と変わらなくなる。

LanceDBの全文検索はTantivyベースで、`baseTokenizer` のデフォルトは `"simple"`。
これは**空白と句読点を区切りとして分割する**トークナイザである。日本語は分かち書きしないため、
このままでは日本語文が意図通りにトークン化されない懸念があった。

これは黙って劣化するタイプの問題である。エラーも警告も出ず、検索結果が空になるだけなので、
最終スコアだけを見ても「エージェント化に効果がなかった」という誤った結論に着地してしまう。
比較実験を始める前に実測で潰す必要があった。

## 実測1: 合成データ（インデックス構築前の事前検証）

合成した日本語チャンク10件（技術記事を模した文体）に対して10個の日本語検索語を投げ、
正解チャンクが上位5件に入るかを `baseTokenizer` ごとに計測した。
LanceDB `@lancedb/lancedb@0.33.0` / Node.js v24.18.1 / Windows 11。

| baseTokenizer | 合格 | 備考 |
|---|---|---|
| `simple`（デフォルト） | **0/10 (0%)** | 全クエリで**ヒット0件**。劣化ではなく完全な機能不全 |
| `icu` | 10/10 (100%) | 外部モデル不要 |
| `icu/split` | 10/10 (100%) | 同上 |
| `ngram` (min=2, max=3) | 10/10 (100%) | 同上 |

## 実測2: 実コーパス（Qiita記事20本 / 455チャンク）

`npm run verify-fts -- --compare` による。コーパスから自動抽出した識別力の高い日本語語彙25件で、
正解チャンクが全文検索の上位10件に入るかを測定。

| baseTokenizer | 合格 |
|---|---|
| `simple`（デフォルト） | **4/25 (16%)** |
| `icu` | 23/25 (92%) |
| `ngram` (min=2, max=3) | 25/25 (100%) |

`simple` が合成データの0%から16%に上がったのは、実記事に `LanceDB` `Mastra` のような
ASCII の技術用語が含まれ、それらは空白・句読点区切りでもトークン化されるため。
逆に言えば**日本語語彙はほぼ引けていない**。デフォルト設定のまま進めていた場合、
パターン2のBM25側の寄与は日本語クエリに対して実質ゼロであり、
ハイブリッド検索はベクトル検索とほぼ同一の挙動になっていた。

`icu` の失敗2件は内訳を見ると軽微だった:

- `"依然"` → ヒット0件。本文が「依然として」で、ICUがこれを1トークンに切ったため部分語で引けない
- `"構築手順"` → `構築`/`手順` に分割され、両語を含む他チャンクに埋もれて上位10件から溢れた

いずれも**辞書ベース分割の語境界に起因する挙動**であり、`simple` のような機能不全ではない。
かつ失敗した2語はどちらも一般語彙で、BM25に期待している役割（専門用語・固有名詞の完全一致）
からは外れている。

## 決定

`baseTokenizer: "icu"` を採用する。

- **`simple` は却下** — 日本語で機能しないことが実測で確定した
- **`icu` を採用** — ICUの辞書ベース単語分割。100%を達成しつつ**外部モデルのダウンロードが不要**で、
  `LANCE_LANGUAGE_MODEL_HOME` の設定もいらない。セットアップの再現性が高く、
  他の環境でこのリポジトリを動かす際の詰まりどころを増やさない
- **`ngram` は実コーパスで100%を出したが、それでも既定にしない** — 理由は下記「測定の限界」を参照。
  数値上は `icu` を上回るが、**この差は測定方法の副作用であって検索品質の差とは言い切れない**。
  保険として残す
- **`lindera/ipadic` は現時点で不採用** — 形態素解析としては最も筋が良いが、外部辞書の配置と
  環境変数設定が必要になる。`icu` が100%を出している以上、その追加コストを払う根拠がない

## 測定の限界（`ngram` の100%を額面通りに受け取らない理由）

`verify-fts` のプローブは「チャンク本文から抜き出した語で検索し、その元チャンクが上位に返るか」
を見ている。**この設計は構造的に `ngram` に有利**である。ngramは部分文字列一致なので、
本文中に確実に存在する文字列を投げれば、ほぼ定義上マッチするからだ。

つまり `ngram` の 25/25 は「BM25のランキングが優れている」ことの証拠ではなく、
「部分文字列検索が部分文字列を見つけられる」というほぼ同語反復に近い。
一方で ngram は転置索引が肥大し、無関係な複合語の内部に偶然一致する
スプリアスマッチを生むため、**BM25のスコアリング品質（順位付け）はむしろ劣化しうる**。

このプローブが答えられるのは「BM25が根本的に壊れていないか」までであって、
「どのトークナイザが最良のRAG検索を与えるか」ではない。後者は Phase 5 で
golden set に対する retrieval-recall@5 を実測して初めて判断できる。

したがって現時点では、トークンの意味的な妥当性と索引サイズで勝る `icu` を既定とし、
Phase 5 の実測で `icu` の取りこぼしが retrieval-recall に効いていると分かった段階で
`ngram` への切り替えを再検討する。

## 帰結

- `FTS_TOKENIZER` は環境変数で上書きできるようにしてある。実コーパスで `icu` の合格率が
  落ちるようなら `lindera/ipadic` を試す余地を残した
- `npm run verify-fts` を Phase 2 に進むための**必須ゲート**とした。合格率80%未満で
  exit code 1 を返す。実コーパスでの再検証がCIでも回せる
- `npm run verify-fts -- --compare` でトークナイザを張り替えながら合格率を比較できる。
  埋め込みを再計算しないためAPIコストはかからない
- 実コーパス（20記事 / 455チャンク）での再測定を完了し、上記「実測2」に記載した。
  `icu` 92% で Phase 2 へのゲートを通過している
- **Phase 5 で再訪すること。** golden set に対する retrieval-recall@5 が出たら、
  `FTS_TOKENIZER=ngram` で再構築して同じ指標を測り、実タスクでの優劣を確定させる

## 補足: RRFとの区別

LanceDBのハイブリッド検索は、BM25の結果集合とベクトル検索の結果集合を融合する
ステップを必ず要求し、既定は `RRFReranker`（Reciprocal Rank Fusion）である。
これは**順位の統計的融合**であって、Cross-Encoderによる意味的な再スコアリングではない。
本プロジェクトが見送ったのは後者（`0005-no-cross-encoder-rerank.md`）であり、
RRF融合はハイブリッド検索の必須構成要素として使用している。

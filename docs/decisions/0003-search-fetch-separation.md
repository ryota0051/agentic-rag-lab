# 0003. search と fetch を分離する（一体型にしない）

- ステータス: 採択
- 日付: 2026-08-08
- 関連: `src/search/fetch.ts`, `src/workflows/agentic-rag/search-fetch-loop.ts`

## 背景

検索スキルの内部構造には2つの選択肢がある。

- **一体型**: `hybrid_search(query)` が候補取得と本文取得をまとめて行い、本文まで返す
- **分離型**: `search(query)` は軽量な参照（chunk_id・タイトル・スニペット・スコア）だけを返し、
  `fetch(chunk_ids, scope)` で初めて本文を取得する

architecture.md の初版では「学習用プロトタイプとしては、まず一体型で動かして感触をつかみ、
範囲拡張の必要性を感じたら分離型に発展させる」と書いていた。

## 決定

**最初から分離型を採用する。**

## 理由

一体型でも比較実験は成立するが、**パターン2とパターン3の差分が「ループの有無」だけに
縮退してしまう**。

分離型にすると、パターン3は「どこまで読むか」という判断をもう一つ持てる。

- `chunk_only` … そのチャンクだけ
- `with_neighbors` … 前後1チャンク（境界にまたがる記述を拾う）
- `whole_section` … 同じ見出しのセクション全体（章単位で読む）

エージェント的RAGの主張は「検索と読解を反復し、必要に応じて掘り下げられること」である。
読む範囲の判断はその主張の中核であり、そこを削ると**エージェント化の効果を過小評価する
実験になる**。実装コストは fetch 側の数十行に過ぎず、得られる観測軸に見合う。

## search が本文を返さないことの意味

分離の効果は「search が本文を返さない」ことに依存している。
search がスニペットではなく本文まで返すと、エージェントは fetch を呼ばずに
スニペットだけで回答を組み立ててしまい、分離した意味が消える。

そのため `SNIPPET_CHARS = 200` と短く設定し、ツールの description にも
「本文は返らないため、読むべきと判断した候補は fetch で取得すること」と明記した。

## 帰結

- パターン1・2も本文取得は `fetch(..., "chunk_only")` を通す。
  検索方法だけを変数にするため、本文取得の経路は3パターンで共通にした
- `fetch` にコンテキスト予算（既定6000文字）と重複除去、
  同一ループ内の再取得を防ぐキャッシュを実装した
- 実験ログでは「パターン3がどの scope を選んだか」も観察対象になる

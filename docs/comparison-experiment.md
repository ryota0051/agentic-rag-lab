# 3パターン比較実験の設計

「普通のRAGとエージェント的RAGは何が違うのか」を、**検索精度の改善**と
**エージェント化（ループ）による効果**に切り分けて観察するための実験構成。

実行: `npm run eval` → 結果は `experiments/YYYY-MM-DD-*.md` に出力される。

## 3パターン

すべて**同一のLanceDBインデックス**（同一コーパス・同一チャンク分割・同一埋め込み）を共有する。

| # | パターン | 検索 | ループ | 実装 |
|---|---|---|---|---|
| 1 | ナイーブRAG | ベクトル top-5 | なし | `src/workflows/naive-rag.ts` |
| 2 | ハイブリッド | BM25＋ベクトル（RRF融合）top-5 | なし | `src/workflows/hybrid-rag.ts` |
| 3 | エージェント的RAG | ハイブリッド top-8 | あり（turn上限3） | `src/workflows/agentic-rag/` |

- 1 → 2 の差 = **検索精度の改善による効果**
- 2 → 3 の差 = **エージェント化による効果**（検索器は同一なので、差はループと範囲判断のみ）

## 公平性のための不変条件

比較の妥当性はこれらに依存している。破ると実験が無効になる。

1. 3パターンは同一インデックスを共有する
2. 生成モデルとプロンプトは共通（`src/shared/llm-client.ts` / `answer-prompt.ts` に唯一の定義）
3. 埋め込みは ingestion と検索で同一
4. 最終的にプロンプトへ入る根拠は **k=5 が上限**。パターン3も fetch 後に切る
5. 3パターンとも同一形状（`RagRunResult`）を返す

> 4 は**上限**であって下限ではない。パターン3は自分の判断で 2件しか取らないこともある。
> 少ない根拠で当てたのか多く取って当てたのかを見るため、`平均根拠件数` も併せて記録している。

### 直接回答スキルだけはプロンプトが別

パターン3が `direct` を選んだ経路のみ、文書接地プロンプトではなく直接回答専用プロンプトを使う。
不変条件2の例外に見えるが、この経路は**文書を1件も持たず、パターン1・2は決して通らない**。

共通プロンプトを流用すると、挨拶に対して「提供された文書からは判断できません」と答えてしまい、
スキル選択が正しく direct を選んでいても回答が破綻する（実際に起きたため分離した）。

## golden set の2バケット

`evals/golden-set.json`。**easy と multihop を分けて集計することが要点。**

| バケット | 作り方 | 役割 |
|---|---|---|
| `easy` | 1チャンクから質問を生成。正解 chunk は1件 | **対照群。** 単発検索で recall がほぼ天井に張り付く |
| `multihop` | 別記事の2チャンクを組み合わせないと答えられない質問。正解 chunk は2件 | **主戦場。** 単発 top-5 では片方しか取れず、ループが効きうる |

### なぜ multihop が必要だったか

当初は easy だけで作ったが、単発ハイブリッド検索の recall@5 が **100%** に達した。
単発が満点ならエージェント化に改善の余地は構造的に存在せず、
「ループはコストが増えるだけ」という、**データの性質に由来する結論**しか出ない。

`npm run probe:retrieval` が伸びしろ（単発ハイブリッドの取りこぼし率）を測り、
5%を切ると警告する。これが実験の前提条件チェックになっている。

### 正解判定は厳密

`golden_chunk_ids` が**全件そろって初めて正解**（完全ヒット）。multihop で片方だけ取れても
答えは組み立てられないため、ここを緩めるとマルチホップ質問を用意した意味が消える。
途中経過を見るために部分 recall も併記している。

### 質問の自己完結性

質問文に「この記事では」「本文の」といった**指示語を含めない**。文書が手元にある前提の
質問は、主題を特定する語を持たないため BM25 もベクトル検索も手がかりを得られず、
3パターンとも一様に失敗して差がノイズに埋もれる。
生成時に LLM の自己判定と決定論的な正規表現の両方で弾いている。

### やってはいけないこと

**検索でヒットするかどうかで golden set を絞り込まないこと。** 評価対象の検索器で
評価データを選別することになり、全パターンのスコアが実力以上に嵩上げされる（循環論法）。
フィルタは質問文と回答文の性質だけを見ること。

## 評価軸

| 軸 | 測り方 | 備考 |
|---|---|---|
| 根拠の充足度 | `retrieval-recall`（自作・**LLM不使用**） | **主指標。** 安定・安価でブレない |
| レイテンシ | `RagRunResult.latencyMs` | 単発と複数ターンの体感差 |
| コスト | トークン数、LLM呼び出し回数 | ループのコストが見える |
| ターン数分布 | パターン3のみ | 何ターンで収束したか、上限到達率 |
| スキル選択精度 | `boundary-cases.json` に対する Precision / Recall | パターン3のみ |
| ツール使用 | `RagRunResult.toolUse`（`ToolUseStats`） | パターン3のみ。生成バックエンドを差し替える実験の主指標 |

### ツール使用は「失敗」を先に読む

`toolUse` の数値を読むときは、まず `structuredOutputFailures` と `searchBlockedCalls` を見る。

スキル選択・充足チェック・確信度チェック・質問分解は、いずれも判定に失敗すると
**もっともらしい既定値へフォールバックする**（無限ループを防ぐための設計）。
そのため計測が無いと、モデルがツールを使えていない状態が
「ターン数中央値1、ループが働かなかった」という**誤った観測**に化ける。

`structuredOutputFailures` が0でない実験では、ターン数分布とスキル選択精度は
「モデルの判断」ではなく「フォールバックの結果」を含んでいる。
レポート生成側がこの場合に警告文を自動で差し込むので、消さずに残すこと。

`fetchScopes` の分布は「どこまで広げて読むかを自分で決める」という
search/fetch 分離の狙い（`decisions/0003`）が機能しているかの直接指標。
`chunk_only` に張り付いていたら、分離した意味が出ていない。

### スキル選択は boundary-cases で測る

golden set 側で測ると全問 search が正解になり、境界の判定能力が見えない。
`evals/boundary-cases.json` に「雑談に見えて固有名詞を含む」「専門用語風だが一般知識で
答えられる」といった境界例を用意し、`expected_skill` を付けてある。

ラベルは主観ではなく**非対称設計の意図**に従って付けている
（固有名詞が少しでも含まれれば `search`）。正解率ではなく Precision / Recall を分けて見る。

## パターン3だけを回す

**パターン1・2は検索にLLMを使わないため決定的**で、実行するたびに同じ結果になる
（実測で5回連続まったく同一だった）。パターン3の改修を検証している間、
1・2を回すのは時間とコストの無駄なので、走らせるパターンを選べる。

```bash
npx tsx evals/run-comparison.ts \
  --patterns=agentic \
  --baseline=experiments/raw-2026-08-09e.json \
  --reuse-skill
```

走らせなかったパターンの結果は `--baseline` の生ログから読み込んでレポートに合成する。
`--reuse-skill` はスキル選択の判定も再利用する（description を触っていない回では
再実行の必要がない）。

さらに速く方向性だけ見たいときは `npm run smoke`（前回の失敗群＋成功群を各6件、約3分）。

## 難易度で絞る

`--difficulty=multihop`（または `easy`）で golden set を絞れる。

ローカルバックエンドは単一GPUで実質直列になり、全46問×3パターンは長時間になる。
エージェント化の主戦場は multihop なので、まずそこだけを回すのが実用的
（easy は単発検索が天井に張り付いていて差が出にくい）。

```bash
npm run eval -- --difficulty=multihop
```

レポートと生ログのファイル名には**バックエンドと難易度が入る**（`--slug=` で上書き可）。
固定名のままだと、同じ日にクラウド版とローカル版を回したときに互いを上書きしてしまい、
「1実験1ファイル」の約束が壊れるため。

## 実行上の注意

- **レート制限**: `gpt-5.6-luna` の TPM 上限は 200,000。エージェント的RAGは1問1万トークン超を
  使うため、並列数を上げると 429 に当たる。既定は並列2（`EVAL_CONCURRENCY` で変更可）
- **ローカルバックエンド**: 並列の既定は1。単一GPUを奪い合うだけで得がなく、レイテンシ計測も歪む。
  本番実行の前に `npm run verify-local-llm` を必ず通すこと
  （ツール呼び出しと構造化出力が成立しない状態で回すと、結果が丸ごと無意味になる）
- **失敗耐性**: 個別の失敗は指数バックオフでリトライし、それでも駄目なら記録して次へ進む。
  パターンごとに `experiments/raw-latest.json` へチェックポイントを書く
  （初回実行では終盤の 429 で数十分ぶんの結果が全損した）
- レポートの「実行の欠損」節に失敗件数が出る。母数が減っている場合は割合で比較すること

## レポートの読み方

**考察セクションは自動生成されない。** 数値の羅列で終わらせず、以下を自分の言葉で埋める。

- multihop で差がついたか。ついたなら何ターン目で回収できていたか
- easy では差がないのにコストだけ増えているか（＝エージェント化の損益分岐点）
- 勝った質問と負けた質問に共通する性質は何か
- スキル選択が Recall > Precision になっているか（非対称設計が意図通りか）

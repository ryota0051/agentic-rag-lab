## 埋め込み軸での直接比較

**この実行は `2026-08-16-local-qwen3.8-27b.md` と生成バックエンドが同一（ローカル Qwen3.8-27B）で、
違いは埋め込みだけ。** したがって multihop の数値は埋め込み軸の直接比較として読める。

| multihop (26問) | 8/16: `text-embedding-3-large` (3072d/API) | 9/2: `ruri-v3-310m` (768d/CPU) | 差 |
|---|---|---|---|
| naive 完全ヒット | 50% | **42%** | −8pt（−2問） |
| naive 部分recall | 73% | 71% | −2pt |
| hybrid 完全ヒット | 65% | 65% | **±0** |
| hybrid 部分recall | 83% | 83% | **±0** |
| **agentic 完全ヒット** | 58% | **73%** | **+15pt（+4問）** |
| **agentic 部分recall** | 79% | **85%** | **+6pt** |
| agentic 勝敗（対hybrid） | 5勝7敗（net −2） | 6勝6敗（net 0）※46問全体 | — |

**単発ベクトル検索は劣化したのに、ループを回すパターンだけ改善した。**
naive の 50%→42% は事前の `probe:retrieval`（13/26→11/26）と完全に一致しており、
純ベクトル検索の劣化は再現性がある。一方で hybrid は完全に同値、agentic は +4問。

なぜこうなるのかは**まだ説明できていない**。仮説としては、ruri の768次元空間は
BM25 と取りこぼす対象が違い、ターンをまたいで検索するパターン3では
その差が候補の多様性として効く、というものが考えられる。ただし 26問で +4問であり、
**ノイズと区別できる差ではない。** 「ローカルの小型埋め込みに落としても
エージェント的RAGは劣化しなかった」までが今回言えることで、
「ローカルの方が強い」は現時点では主張できない。

なお hybrid について、事前の `probe:retrieval` は 3-large で 16/26 (62%) を出したが
8/16 の eval は 65% だった。probe は検索単体、eval はワークフロー経由という
**計測器の違い**があり、加えて `index-openai-3large` は今回作り直したものなので
再埋め込みによる微小な数値差でタイブレークが変わった可能性がある。
この2つの数値を同一視しないこと。

## 考察

**multihop で差はついた。** agentic 73% は hybrid 65% を上回り、
`0009`（エージェント化の損失分解）以来はじめて**ローカルモデルでも
パターン3が単発ハイブリッドを超えた**。8/16 の 58% では負けていたので、
埋め込みを変えただけで勝敗がひっくり返ったことになる。
ターン数の中央値は3で 8/16 と変わらず、回収は主に2〜3ターン目で起きている。

**easy では差がないどころか、コストだけ増えて精度が落ちている。** これが損益分岐点。

| easy (20問) | 完全ヒット | 平均レイテンシ | 平均LLM呼び出し | 平均入力トークン |
|---|---|---|---|---|
| hybrid | **100%** | 6.0秒 | 1.0 | 1,507 |
| agentic | 90% | **43.2秒（7.2倍）** | 7.0 | 11,608（7.7倍） |

**7倍のコストを払って10pt悪化している。** 原因は根拠の絞り込みで、agentic の
平均chunk数は 2.5・根拠文字数 1,453 と、hybrid の 5.0 / 2,536 の半分近くしかない。
単発で引ける質問に対してエージェントが「もう十分」と早期に打ち切り、
k=5 の枠を使い切っていない。**easy にルーティングしない仕組みがない限り、
パターン3を常用する理由はない。**

**勝った質問と負けた質問の性質。** 勝った6件はすべて「2つの異なる記事の設定を
突き合わせる」形（LLaVA と LLaVA-Med、Qwen3-14B と Qwen3-8B-FP8、
CIFAR-10環境と vLLM環境）で、1回の検索では片側しか引けない構造を持つ。
これは分解と再検索が効く典型で、設計の狙い通り。

負けた6件のうち2件（「データ拡張手法をすべて挙げてください」「LLaVA論文では…
どのチューニングを実施していますか？」）は**単発で引ける質問**であり、
easy バケットの悪化と同じ現象。残り4件は multihop だが、
「〜の場合はどのような通信上のボトルネックを確認すべきですか」のように
**正解チャンクが1記事内に固まっている**ものが多い。
つまりパターン3が負けるのは「探索が足りない」ときではなく「**探索しすぎて
根拠を絞りすぎる**」ときで、失敗の方向が一貫している。

**スキル選択は Precision = Recall = 100% で、非対称設計の意図は満たしている**が、
両方100%なので今回のケースでは設計の効き目を確認できていない
（8/16 も100%。boundary-cases 20件がローカル27Bには易しすぎる）。
取りこぼし0件は重要で、`0001` のルーティングはローカルモデルでも壊れていない。

**構造化出力の失敗が0件**なのは今回も維持されている。`0013` が警戒した
「フォールバックに倒れて、ループが働かなかったという誤った観測が出る」状態には
なっていないので、上記の数値はそのまま読んでよい。

### ツール使用について（8/16 と直接比較してはいけない）

今回は46問（easy含む）、8/16 は26問（multihop のみ）なので、
**1問あたりの平均値は母集団が違う**。easy は検索が少なくて済むため、
search 0.85→0.46 / fetch 2.23→1.59 の低下は埋め込みの効果ではなく
easy が混ざったことの効果とみるのが自然。ターン数分布の
「1ターンで完結 1件→8件」も同じ理由で、パターン3が怠けるようになった証拠ではない。

比較したいなら `--difficulty=multihop` で取り直すこと。

そのうえで気になるのは **fetch 未解決ID が 0.08/問 → 0.26/問（3倍）** に増えている点。
これは存在しないIDの生成とコンテキスト予算切れの合算なので、
どちらが増えたのかを raw JSON と突き合わせる必要がある。前者ならローカル埋め込みとは
無関係な生成側の問題、後者なら根拠が増えたことの副作用で、意味がまったく違う。

`chunk_only` の比率が 12%→23% に上がり `with_neighbors` が 57%→42% に下がっているのも、
easy 混入で説明がつく範囲か切り分けが必要。

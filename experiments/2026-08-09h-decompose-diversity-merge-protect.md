## 考察

### 1. multihop で初めて hybrid を明確に上回った

(f) までは実質同点（17 vs 17 / 68%）だったが、今回は 73% vs 65% で agentic が勝った。
部分recallも 87% vs 83%。分解・多様化・主クエリ保護マージの3点セットで、
「エージェント化しても精度は変わらない」という (f) の結論を初めて覆した。

中央値ターン数が (f) の 1 → 3 に上がっている。これは主に分解・多様化自体が
`queryTrace` に自分のクエリを積むため（`0010`/`0011` の設計）で、
エージェント自身の言い換えループが3倍働くようになったわけではない
（1ターンで完結した件数は (f) の 28 件 → 今回 5 件だが、これも同じ理由でカウントの意味が変わっている）。

### 2. easy はヒット率不変なのにコストだけ増えた

easy は (f) と同じ 95%。ところがレイテンシは 10198ms → 15952ms、
入力トークンは 12559 → 15270 に増えている。原因は `diversifySeed`
（`0011`）で、**easy 質問は単一記事・単一トピックという設計上、
上位5件がほぼ必ず1記事に偏る** ため、多様化がほぼ毎回誤発火し、
無駄なハイブリッド検索（埋め込み1回＋DB検索1回）を毎回払っている。
最終的に fetch するかはエージェント判断に委ねているため精度への実害はなかったが、
**「効果のない多様化に払うコスト」は easy 側でそのまま可視化された**。
閾値（`DIVERSITY_CHECK_TOP_N`）を難易度で分けずに全問一律にした設計の代償で、
次にコストを詰めるならここが対象になる。

### 3. 勝った質問と負けた質問の性質

勝った5問はいずれも「AではX、BではYですか」のように**表層で対象が分離できる**
比較質問（Docker Composeの設定比較、Vite+Docker と Jupyter の依存導入比較など）。
分解（`0010`）が正しく発火するタイプで、狙い通りの効果が出ている。

負けた4問のうち3問（RAGコスト、Rayヘッドノード、日本語RAG）は、依然として
**質問文からは2記事構成と読み取れない**ため分解は発火せず、多様化は発火して
除外記事側を検索するものの、**その検索自体が正解チャンクを上位8件に見つけられない**。
これは統合方法（`0012`）ではなく埋め込み/BM25の検索力そのものの限界で、
今回の3点セットでは解決しない別の課題として残る。残り1問（LLaVA論文）は
そもそも single-chunk 問題で multihop の仕組みとは無関係な素の検索順位ミス。

### 4. スキル選択は不変

description を触っていないため (f) の判定結果をそのまま再利用。
Recall 100% / Precision 100% で、非対称設計の意図（取りこぼしゼロ優先）は維持されている。

### 5. 今回の教訓

複数クエリの検索結果を統合する際、**実績のあるクエリ（今回は主クエリ）の候補を
無条件に守り、追加クエリは「competing」ではなく「supplementary」として扱う**設計が
効いた。逆に言うと、(g) で見たように生スコアでの統合は一見自然に見えて、
異なるクエリ間のスコア比較可能性という暗黙の前提が壊れているだけで簡単に regression する。

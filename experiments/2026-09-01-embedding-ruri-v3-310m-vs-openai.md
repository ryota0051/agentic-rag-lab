# 埋め込み軸: ruri-v3-310m（ローカル/CPU） vs text-embedding-3-large（クラウド）

> **これは retrieval 単体の実験であり、3パターン比較（`npm run eval`）は回していない。**
> 測っているのは `npm run probe:retrieval`、つまり生成を一切挟まない検索段階の recall のみ。
> 埋め込みを変えたときの3パターン比較は別途 `--slug=` を付けて実施すること。

- 実施日: 2026-09-01
- 変数: **埋め込みモデルのみ**（`EMBEDDING_BACKEND`）
- 固定: golden set 46問 / チャンク分割（455チャンク・20記事）/ FTSトークナイザ `icu` / k=5
- 生成バックエンド: この実験では生成を使わないため無関係
- 関連ADR: [`0014-local-embedding-backend.md`](../docs/decisions/0014-local-embedding-backend.md)

## 構成

| | A: クラウド（既定） | B: ローカル |
|---|---|---|
| モデル | `text-embedding-3-large` | `ruri-v3-310m`（Targoyle GGUF Q8_0 / 337MB） |
| 次元 | 3072 | 768 |
| pooling / prefix | — | mean / `検索クエリ: ` `検索文書: ` |
| 実行環境 | OpenAI API | `ghcr.io/ggml-org/llama.cpp:server-b10450` **CPU**（`-ngl 0`, 16スレッド） |
| インデックス | `data/index-openai-3large/` | `data/index-ruri-v3-310m/` |
| 埋め込みスループット | 56.7 件/s | 5.1 件/s（455チャンクで約1.5分） |

## 結果

| | A: 3-large (3072d/API) | B: ruri-v3-310m (768d/CPU) | 差 |
|---|---|---|---|
| easy ベクトル検索 完全ヒット | 19/20 (95%) | 18/20 (90%) | −1問 |
| easy ベクトル検索 部分recall | 95% | 90% | −5pt |
| easy ハイブリッド 完全ヒット | 20/20 (100%) | 20/20 (100%) | ±0 |
| easy ハイブリッド 部分recall | 100% | 100% | ±0 |
| multihop ベクトル検索 完全ヒット | 13/26 (50%) | 11/26 (42%) | −2問 |
| multihop ベクトル検索 部分recall | 73% | 71% | −2pt |
| **multihop ハイブリッド 完全ヒット** | 16/26 (62%) | **17/26 (65%)** | **+1問** |
| **multihop ハイブリッド 部分recall** | 81% | **83%** | **+2pt** |

単発ハイブリッドの取りこぼし（＝パターン3の伸びしろ）は A が 38%、B が 35%。
どちらも「差が観測できる水準」の判定。

## 定性観察

**純ベクトル検索では3072次元のクラウドAPIが勝ち、ハイブリッドでは768次元のローカルが勝った。**
これがこの実験で一番おもしろい点で、しかも一貫している（easy でも multihop でも
ベクトル単体は A ≧ B、ハイブリッドは A ≦ B）。

素直な解釈は「ruri はベクトル単体の網羅性でわずかに劣るが、BM25 と**取りこぼす対象が違う**」。
RRF は2つの順位を融合するので、ベクトル側が BM25 と相関しすぎると融合の利得が小さくなる。
日本語特化モデルは語彙的な手がかりに引きずられにくく、BM25 と補完しあった可能性がある。
ただしこれは 26問での +1問の差であり、**統計的に主張できる差ではない**。
「ローカルに落としても劣化しなかった」までが言えることで、「ローカルの方が良い」ではない。

**multihop で両方が引けなかった質問はほぼ同一。** A で6問、B で5問あり、うち4問が共通
（Vite×vLLM/Jupyter の Docker 構成、LLaVA/LLaVA-Med の学習段階、CIFAR-10 環境比較、
LLaVA-Med の計算資源とモデル選択）。これらは**埋め込みを変えても解けない**質問群であり、
パターン3（search/fetch ループ）の見せ場が埋め込みの質とは独立に存在することを示している。
埋め込みを改善してもここは埋まらない、というのは記事の主張として使える。

A だけが落とした2問、B だけが落とした1問（vLLM の M3-Embedding 実行結果と dense_vecs の次元数）
は入れ替わっており、系統的な弱点の違いとまでは言えない。

**BM25 は両インデックスで完全に同一の結果**（`verify-fts` 23/25 合格、失敗した検索語
「依然」「構築手順」も同一）。FTS が埋め込みに依存しないことが実測で確認できた。
`chunk_id` も両インデックスで一致し（`validate:golden` 全件OK）、golden set は
埋め込みをまたいでそのまま有効。

## 事前チェック（`npm run verify-embedding`）

ruri-v3-310m での実測値。

| 項目 | 結果 |
|---|---|
| 次元 | 768（設定と一致） |
| 正規化 | サーバの生ノルム = 1.0000（**llama.cpp 側で既に正規化済みだった**） |
| 決定性 | 同一文2回の cos = 1.000000 |
| 等方性 | 無関係20文の総当たり cos 平均 0.7470 / 最大 0.8281（崩壊なし） |
| prefix 適用 | query と document の cos = 0.9950（別ベクトルになっている） |
| embedBatch 順序保証 | 19本（バッチサイズ8を跨ぐ）全件が入力順に対応 |
| 意味的サニティ | 関連 0.9507 / 無関係 0.7993 / 差 0.1513 |
| 実コーパス retrieval | 30問/プール120件で top-3 命中率 **100%**（ランダム相当 2.5%） |

生ノルムが 1.0000 だったので `embed.ts` の L2正規化はこのモデルでは実質 no-op。
ただし bge-m3 や別 pooling では非正規化が返りうるので、ガードとしては残す（ADR 0014 参照）。

**prefix の効果は測定できなかった。** 正しい prefix / 文書側 prefix を誤用、どちらも
top-3 命中率 100% で差が出ていない。見出しパスをクエリにするプローブが易しすぎたためで、
「prefix が無意味」の証拠にはならない。より難しいプローブを設計するか、
golden set の実クエリで prefix を外した A/B を取るのが宿題。

## 解消した未検証事項

計画段階の最大リスクは「ruri の GGUF はパッチ版 llama.cpp で変換されており、
ピン留めしたイメージでロードできないかもしれない」だった。

**`ghcr.io/ggml-org/llama.cpp:server-b10450`（CPU版）でそのままロードできた。**
ModernBERT サポートが upstream（PR #15641 / 2025-12-22）に入っており、SentencePiece
トークナイザ経路も含めて本家で動く。パッチ版は変換時にだけ必要だったことになる。
フォールバックの `bge-m3` は使わずに済んだが、プロファイル表と compose サービスは残してある。

## 環境まわりで踏んだこと

- **`docker compose --profile ruri up -d` だけだと生成サーバ（18GB）まで起動する。**
  プロファイルを持たないサービスは常に対象に入る。npm scripts でサービス名を明示して回避した。
  逆にプロファイル指定なしの `docker compose down` はプロジェクト全体を落とすので、
  `serve:local:down` / `serve:embed:down` も `rm -sf <service>` に変えてある。
- 生成サーバと埋め込みサーバは**同時に healthy で動作**。`nvidia-smi` で 19756MiB（生成モデルのみ）、
  埋め込みコンテナは起動ログで `no usable GPU found` と出て VRAM を一切使っていない。
  この状態で `npm run verify-local-llm` の3項目（素の生成 / ツール呼び出し / 構造化出力）も全通過。
- 生成サーバは 17.5GB の GGUF をバインドマウント経由で読むため、起動に約19分かかった
  （`start_period: 60m` が想定している通り）。埋め込み側は 29秒。

## fingerprint ガードの動作確認

意図的に壊して、3つとも日本語で throw することを確認済み。

1. 未構築プロファイル（`bge-m3`）→「テーブルがありません（data/index-bge-m3）」
2. `index-meta.json` のモデル名と pooling を書き換え（**次元は768のまま**）
   →「インデックスと現在の埋め込み設定が食い違っています」＋不一致項目の列挙
3. `index-meta.json` を削除 →「どの埋め込みモデルで作られたか検証できません」

2 が本命。次元が同じで中身が違うベクトル空間という、エラーにならない破滅ケースを捕まえられている。

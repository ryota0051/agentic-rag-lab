## 考察

### 検索側が本当に固定されていたことの確認

naive と hybrid の retrieval-recall が **26問すべてで完全に一致**した（完全ヒット・部分recall とも）。
埋め込みとインデックスを触らずに生成モデルだけを差し替えるという設計が、
意図どおり機能していることの直接的な裏付けになっている。
以降で見える差は、すべてエージェントを駆動するLLMに由来すると言ってよい。

### ツール使用は激減したが、精度は落ちていない

これが今回の主要な発見。ローカルモデルのツール呼び出しは
**fetch が 8.58 → 2.23（3.8分の1）、search が 2.33 → 0.85** と大幅に少ない。
ターン数中央値も 4.5 → 3 に下がっている。

にもかかわらず精度は落ちていない。レポート上の「63% vs 58%」は**母数の違いによる見かけの差**で、
クラウド側は 429 で2問欠損しているため n=24、ローカルは n=26 になっている。
**共通の24問だけで突き合わせると、両者とも 15/24（62.5%）で完全に同じ**だった。

| 共通24問での内訳 | 件数 |
|---|---|
| 両方正解 | 11 |
| クラウドのみ正解 | 4 |
| ローカルのみ正解 | 4 |
| 両方不正解 | 5 |

正解数は同じだが**中身は入れ替わっている**（各4問ずつ相手が落とした問題を拾っている）。
つまり「ローカルは劣化版」ではなく、**振る舞いの異なるエージェント**として観察するのが正しい。

ここから言えるのは、このタスクでは
**ツール呼び出しの多さが精度に直結していなかった**ということ。
クラウド側は1問あたり8.58回も fetch し、根拠文字数も 4208 と多く集めていたが、
最終的にプロンプトへ入るのは k=5 に切られる（不変条件4）。
集めた根拠の大半が上限で捨てられていた可能性が高い。

### scope の選び方が正反対

最も明確な質的差はここ。

- **クラウド**: `whole_section` 69% ＝ 見出し単位で広く読む
- **ローカル**: `with_neighbors` 57% ＝ 前後1チャンクだけ足して狭く読む

`chunk_only` の比率は両者とも12%で同じなので、**「範囲を広げる」判断自体はどちらもできている**。
違うのは広げ方の大胆さで、ローカルは保守的に1段階だけ広げる。
search/fetch を分離した狙い（[0003](../docs/decisions/0003-search-fetch-separation.md)）は、
ローカルモデルでも機能していると言える。

平均根拠文字数が 4208 → 3598 に留まったのは、この控えめな範囲拡張の帰結。
そしてそれでも精度が同じだったのだから、
**`whole_section` で広く読むことの費用対効果は疑わしい**。

### 指示追従性はむしろローカルの方が良い

検索回数の上限超過は **15回 → 3回**。スキル選択の正解率は **90% → 100%**
（クラウドが落とした `hypothetical` と `jargon-but-general` をローカルは正解している）。
「ローカルモデルは指示を守れない」という予想とは逆の結果になった。

ただしスキル選択は境界20件しかなく、1〜2件の差は誤差の範囲。
過剰に読み取らないこと。

### コストの構造が違う

- **入力トークンは半減**（64019 → 30483）。ツール呼び出しが少なくエージェントの会話が短いため
- **出力トークンは倍増**（2395 → 4790）。`reasoning_effort: low` の思考トークンが乗る
- **レイテンシは3.4倍**（36.7秒 → 126.2秒）。ただし直列実行かつローカル生成なので、
  クラウドとの絶対比較にはあまり意味がない

### エージェント化は今回もハイブリッドに勝てていない

ローカル・クラウトどちらでも agentic（58% / 63%）は単発 hybrid（65%）を**下回っている**。
これはバックエンドの問題ではなく、両者に共通する現象。
ローカル導入とは独立した既存の課題であり、`0012` の主クエリ保護や
RRF順位融合への置き換えといった宿題がそのまま残っている。

## 実験条件に関する注意

- **`reasoning_effort` は `low`。** unsloth のドキュメントは `none` も挙げているが、
  このGGUF同梱のチャットテンプレートは `xhigh` / `medium` / `low` しか受け付けず、
  `none` を渡すと全リクエストが 500 になる（`npm run verify-local-llm` が事前に検出した）。
  思考トークンが完全にゼロではない点に注意。
- **各条件1回のみの実行**で、繰り返しによる分散の評価をしていない。
  n=26 に対して数ポイントの差は誤差の範囲として扱うこと。
  今回「共通24問で完全に同数」という結論が出せたのは、たまたま差が0だったからではなく、
  母数を揃えて突き合わせたから。**レポート上の百分率をそのまま比較しないこと。**
- 構造化出力の失敗が両者とも0件なので、ターン数分布とスキル選択精度は
  フォールバックではなくモデルの実際の判断を反映している。
- サーバ設定（文脈長24576・KV q8_0・サンプラー）は `docker/compose.yaml` に固定。
  イメージは `ghcr.io/ggml-org/llama.cpp:server-cuda-b10450`。VRAM実測 20.4GB / 24.5GB。

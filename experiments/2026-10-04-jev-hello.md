# Jev を触ってみた（判定専用モデルは「検索は十分か？」に使えるか）

- 実施日: 2026-10-04
- Jev: `jev-latest` → 実体 `jev-1.13.0`
- 比較用 LLM（ケース4のみ）: `openai/gpt-5.6-luna`（既存の `checkEvidence`）
- 生成スクリプト: `scripts/jev-hello.ts`（生データ: `experiments/raw-2026-10-04-jev-hello.json`）
- Jev 呼び出し 27 回 / 入力 42,287 トークン / 概算 $0.00178 / レイテンシ中央値 176ms（最大 238ms）
- 参考: LLM 判定のレイテンシ中央値 5376ms（3 回）

## やってみて分かったこと

- **速い・安い。** 1回 150〜240ms で、27回投げて合計 $0.002 弱。同じ判定を LLM（checkEvidence）にさせると 3.6〜5.4 秒かかり、**約25倍の差**がある。
- **「根拠で答えられるか」はきれいに分かれた。** 十分 84% ／ 片方欠け 8% ／ 無関係 2%。score 型で聞くと「全部／一部／なし」の3段階が、確信度ほぼ 1 で返ってきた（ケース3）。
- **同じ入力ならほぼ同じ値が返る。** 3回投げて 8% / 7% / 8%。完全に決定的ではないが、±1pt に収まった（ケース4）。
- **間違えるときは自信がない。** 日本語のスキル分岐で期待と逆になった2問は、confidence が 0.25 / 0.53 と低かった。正解した direct 側は 0.94〜1.00（ケース2）。**閾値を掛ければ救える間違い方**で、ここが LLM の二値判定といちばん違う点。
- **ただし「プロンプト」の仕事は無くならない。** criteria（選択肢の説明文）を書き換えると、「トークンとは何ですか？」の p(search) が 25% → 89% → 0% と大きく振れた（ケース6）。判断基準をどう言葉にするかは、引き続き人が考える必要がある。
- **口語の言い換えには少し弱い。** 「十分」の確率は、原文 86% → 言い換え 79% → 砕けた口語 66% と下がった。一方「片方欠け」は 8〜9% のまま動かない。**「足りない」の検出は頑健で、「足りている」の確信のほうが揺れやすい**（ケース5）。
- **ハマりどころ**: Git Bash から curl で日本語を送ると `400 There was an error parsing the body` になる（Windows の引数エンコーディングが原因）。Node の fetch からなら問題ない。また、score 型の criteria はオブジェクトではなく**配列**で渡す必要がある（オブジェクトで渡すと同じ 400 になる）。
